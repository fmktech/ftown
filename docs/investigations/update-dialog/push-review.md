# R3 — push conflict contract review

The proposed targetless `ON CONFLICT DO NOTHING` on the `push_events` insert is compatible with the current schema and intended duplicate behavior, conditional on the real-PostgreSQL reproduction. Migration 0005 defines exactly the primary-key uniqueness on `id` and natural-tuple uniqueness on `(sub, bridge_id, session_id, event_key)`. `eventIdentity` deterministically hashes that same tuple. Concurrent identical requests therefore should resolve to the same owner-scoped ID even when PostgreSQL reports the natural-tuple constraint instead of the named primary-key arbiter. The artifact shows that exact secondary constraint failure in the existing `ON CONFLICT(id)` statement; it does not by itself prove that the proposed change works under concurrency.

The `created` CTE must continue to be the sole source of delivery snapshot rows. A skipped conflict must not resnapshot later subscribers, replace the winning payload or modify the event; the separate `SELECT ... WHERE id=$1 AND sub=$2` remains mandatory. Keep the current authorization, rate limit, generic payload and claim/lease logic unchanged. Targetless conflict handling covers unique constraints only; NOT NULL, CHECK, and other errors must continue to surface. A natural-tuple collision against an existing row with a different ID must fail closed through the existing owner-scoped lookup (503), not select the row by tuple or deliver it. This also guards inconsistent legacy/manual rows and any hypothetical hash/identity mismatch; do not report those as successful duplicates.

Real-DB acceptance should demonstrate simultaneous identical inserts both succeed, one event row and one first-created recipient snapshot result, with the later subscriber excluded on duplicate replay. Verify the persisted original generic payload, another owner cannot retrieve or claim the row, a natural tuple with a mismatched stored ID fails closed, and invalid non-unique constraints still error. Route/API focused E2E should retain both 202 assertions for concurrent duplicate posts; a mocked query alone cannot validate PostgreSQL's competing unique indexes. No DB, browser, server, CI or application edits were performed by R3. Report lease released.

## R3 — W5 source and harness review

The one-clause source change is consistent with the frozen contract, and root's 50-pair pre-fix run establishes the real SQL failure. The harness retains non-backfill, canonical generic payload, different owner/bridge IDs, mismatched legacy ID, CHECK violation, and 50 synchronized pairs. Two acceptance gaps remain: the pairs have no initial subscriptions and use an older timestamp, so zero deliveries would also pass if first-created snapshot creation broke; add a pre-existing subscription dated before the event and assert exactly one delivery after duplicate/replay, then add a later subscription and assert no backfill. Separate owner IDs do not independently test access to an existing event: assert another owner's `claim` returns no deliveries and `remaining` is zero for the first owner's ID. These are DB harness checks, not a proposed product change. Source approval conditional on the post-fix DB counterfactual and these edge checks. No DB or services executed by R3.

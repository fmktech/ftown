## Identity, storage and consumption contracts

- Child `ftown harness mail send --parent` resolves the target from `FTOWN_PARENT_SESSION_ID`, and identifies the sender from `FTOWN_SESSION_ID` (`bridge/src/harness-commands.ts:372–408`). `acceptMail(session, body)` appends a `MailMessage` addressed to that target session (`bridge/src/mail-delivery.ts:276–308`); a live long-poll waiter is delivered and marked immediately, otherwise a timer is scheduled for non-Pi sessions (`:310–335`).
- Each inbox is session-local `inbox.jsonl`; per-session file operations serialize, `listUndelivered` filters `deliveredAt`, and `markDelivered` atomically marks the specified still-undelivered IDs (`bridge/src/mail-store.ts:28–49,74–89,99–138`). The explicit CLI read resolves its own FTown session from `FTOWN_SESSION_ID`, falling back to workspace registry (`bridge/src/harness-commands.ts:366–369,416–438`), and calls the per-session inbox endpoint via `fetchInbox` (`bridge/src/cli-client.ts:71–77`, `bridge/src/local-api-server.ts:1165–1195`). `(no mail)` means that non-peek read returned no messages, not that storage is proven lost.
- `readMail(session, {wait, peek, all, limit})` with `peek` inspects without marking; a normal non-peek read marks all currently undelivered IDs and returns them (`bridge/src/mail-delivery.ts:346–380`). The Codex installer registers `hook-pump` for Stop, UserPromptSubmit and SessionStart (`bridge/src/codex-installer.ts:12–13,90–94,136–149`). The hook resolves the same FTown session environment/registry and calls the same non-peek `fetchInbox` at turn boundaries (`bridge/src/harness-commands.ts:470–487,492–514,532–539`); it may consume messages that an explicit read would otherwise return. That shared mechanism does not by itself prove which reader consumed the captured messages.
- **H2 remains inconclusive:** the implemented send, FTown-to-native target mapping and explicit read have a coherent intended identity path, but source alone cannot prove which exact runtime identity consumed the capture's messages or exclude a separate identity/configuration issue. The capture evidence worker is examining the actual private proof. Nothing in this source trace establishes message loss.

## Queue timing and cancellation boundary

The accepted-mail timer for Codex fires after five seconds (`bridge/src/mail-delivery.ts:326–335`). `wakeSession` rechecks unread mail and a live matching native identity; the native adapter also calls `isCurrent` immediately before dispatch (`mail-delivery.ts:469–512`, `native-mail.ts:95–100,122–124`). The `agentBusySince` gate occurs **after** the native attempt, so a supported Codex wake can be accepted while a turn is still running (`mail-delivery.ts:492–527`). An accepted or ambiguous admission records batch IDs and suppresses duplicate wake attempts, without consuming messages (`:515–518`). `readMail` does not cancel an already accepted item (`:346–380`). Local `codex-cli 0.164.0`, the capture's pinned version, reports `codex queue --thread <THREAD> --message <TEXT>` and no queue-removal operation in `codex queue --help`; this does not establish whether an undocumented lower-level app-server API can cancel. Do not claim all native cancellation is impossible without checking that separate contract.

Thus the bounded, source-consistent schedule is: (1) the parent is busy; (2) child mail arrives and the native generic pointer is admitted; (3) the active turn or a turn-boundary pump consumes those messages; (4) Codex later processes its already admitted pointer; (5) a fresh normal read yields `[]`. A drain before the wake timer/revalidation is a distinct control: existing test `mail-delivery.test.ts:482–493` checks no legacy nudge after prior consumption, and `:834–853` checks the native `isCurrent` fence after a probe barrier. Neither proves cancellation after native admission. Also, a second new arrival can produce a fresh native wake while an earlier batch is pending (`:492–500`), so any repair must preserve wake-up of genuinely new unread mail and avoid duplicates/loss.

Busy-gating the native dispatch and rechecking on idle may prevent this particular busy-turn schedule, but it is not a complete proof: a turn can begin or mail can be drained after the final pre-dispatch check; an already admitted pointer is outside the current adapter's cancellation interface. A safe repair requires an explicit delivery/queue contract and targeted proof of liveness, not simply changing the displayed copy. Whether a stronger execution-time check or reliable cancellation is available remains unverified. Retain the current unknown-admission rule: ambiguous dispatch must not be retried blindly (`native-mail.ts:125–134`, `mail-delivery.ts:515–518`).

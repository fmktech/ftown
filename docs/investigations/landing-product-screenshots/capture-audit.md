## Existing contracts

- `e2e/helpers/fixtures.ts`: `test` extends Playwright and automatically calls `cleanupBrowserApprovals(info.testId)`. Use this fixture rather than bare Playwright `test` for legacy browser invitations. `e2e/helpers/app.ts`: `sharedEmail()`, `login(page, email, password?, {pairBridge?})`, `waitForBridgeOnline(page)`, `openSession(page, name)`, and `runMarkerInTerminal(page, marker)`. - `e2e/helpers/bridge-api.ts`: `bridgeApiFetch(method, path, {body?, bridgeHome?})` returns `{status, body}`; ordinary business calls use the real encrypted CLI client with the scratch bridge pointer. `POST /api/sessions` with `{shellType: "shell", name: "..."}` returns 201 and `{session: {id, bridgeId}}`. Record only successfully created IDs. `DELETE /api/sessions/<id>` cleans those IDs. Existing attention tests demonstrate this on desktop and mobile.
- `bridge/src/local-api-server.ts:607`: `POST /api/sessions/<id>/attention` takes exactly `{title?, message}`, persists a real notification and publishes it, returning 200 `{event}`. Message is required, nonempty and <=2000 chars; optional title <=200. `e2e/tests/session-tools.spec.ts` proves a shell session exposes this capability. For attention evidence use explicitly demo-labelled requests (e.g. title `Demo review requested`, message `Review the local test results.`); this is real product state, not a claim that an AI provider generated it. Existing tests alternatively send the supported `POST /hook` with `ftown_session_id`, `hook_event_name: "Notification"`, `notification_type: "agent_needs_input"`, title and message. Do not make up provider transcripts.
- `e2e/helpers/account-pairing.ts`: `startAccountTestBridge(origin, accountHint?)` creates its own temporary home and process; `approveAccountComputer(page, bridge)` performs real account pairing and returns bridge ID; `createAccountShell(page, bridgeId, name)` makes a shell; `usePrivateApprovalLink(page)` starts second-browser approval. `stop()` deletes its sessions, terminates its exact child, and deletes its temporary home. `e2e/tests/account-trust.spec.ts` shows the real desktop approval of a named second browser and Security Access map. Account pairing requires trusted local HTTPS origin (`FTOWN_PUBLIC_URL`, normally `https://localhost:8444`), browser NSS fixture and isolated fixture user (`makeUser`/`registerUser`); it does not use the legacy shared-account bridge. Never persist or print approval links, codes, keys, or token-bearing URLs.
- Bridge labels are real machine hostnames, not a proved user-settable rename API. `bridge/src/centrifugo-client.ts:326` publishes `hostname()` in presence; `bridge/src/index.ts:410,548` uses `osHostname()` for pairing/endpoint registration. `ui/src/hooks/useBridges.ts:96` reads presence hostname. Use a benign disposable sandbox hostname chosen before bridge startup if supported by the sandbox; otherwise retain the actual safe sandbox hostname. No evidence supports rewriting presence or DOM to impersonate another machine. Multiple bridges on the same host will naturally share a hostname. Browser labels are supported through real pairing forms and `pairBrowser`.

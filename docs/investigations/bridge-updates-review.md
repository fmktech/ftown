The injected staging tests never exercised actual npm. Minimal fix: distinct private empty config files, keeping registry/cache/environment isolation. Required evidence: the exact old environment fails an offline npm command; the new environment succeeds and still excludes inherited npm/provider/cloud configuration. **Root confirms the actual old configuration failed and reports a passing offline probe after repair.**

2. **P2 — a crashed reservation guard prevents its own advertised repair path.** Original `update-handoff.ts`, `withLockGuard`, created an empty `update-reservation.guard` with exclusive open and no owner information/recovery. `assertUpdateReservationAllowed` rejected any existing guard; both ordinary start and setup call it. A crash in this tiny critical section therefore left even exact-version `setup --repair` permanently blocked despite a dead reservation owner. Minimal fix: exact owned marker/provably-dead recovery with live, malformed, foreign and symlink preservation, matching the existing setup-lock discipline. Required fixture: dead exact owner recovers; live/unknown owner remains untouched; normal start/setup can pass after legitimate recovery.

3. **P2 — timeout cleanup can remain pending forever.** Original `update-release.ts:77–90` and helper `runSetup` sent SIGKILL at the deadline, then settled only on a later `close` event without another bound. The advertised stage/setup deadlines therefore did not bound the failure path. Minimal fix: a bounded termination-proof phase. If exit cannot be proved, signal explicit process uncertainty, keep stage/reservation and freeze admission; do not delete evidence or reopen merely because a timer fired. Required tests cover absent close, confirmed close and coordinator handling of uncertain staging/helper descendants. Root reports P1's first repair adds bounded proof; R1 is implementing matching uncertainty handling.

4. **P2 — the replacement can admit new work before helper acceptance, then lose it on readiness failure.** `index.ts:1009` set business readiness before the private ready exchange at `:1018–1020`. Original helper `update-handoff.ts:272` sent ready ACK before checking/persisting the final receipt/releasing ownership at `:276–282`; its failure path killed the replacement at `:284`. Pause/fail that exchange and a browser can create a new session in the window; subsequent helper failure kills a direct PTY or strands an agent job. Minimal fix: keep replacement mutation/launch admission closed until the final private success acknowledgement, and send that ACK only after helper receipt/ownership finalization. Required fixture: create/revive cannot start while readiness is paused; readiness/receipt failure admits no new work; success reopens only after exact final ACK. Root assigned the coordinated P1/R1 repair.

5. **P2 — a required nonsecret launch setting is dropped on restart.** The original helper's two launch-environment allowlists (including `update-handoff.ts:258–260`) excluded `FTOWN_ALLOW_INSECURE_API`. A canonical opted-in cloud bridge using its explicitly permitted non-loopback HTTP API origin can pass support checks, but its replacement rejects that same preserved descriptor without the setting (`index.ts` existing API-URL guard). Minimal fix: preserve this specific trusted nonsecret setting for replacement, or reject the launch as unsupported before acceptance. Keep staging's secret-free environment. Required fixture: the declared supported launch retains the setting, while arbitrary inherited npm/provider/cloud settings still do not enter installation. Root assigned this narrow P1 change; no general environment forwarding redesign was requested.

# R2 — implementation review

## Findings requiring repair

1. **One unreadable mailbox blocks other linked agents.** `pull-request-events.ts` processes each link with `await withSessionMutation(...)` and does not catch a `commitPullRequestObservation` failure per session. A recognizable malformed checkpoint intentionally makes `MailStore.readInbox` throw; a persistent filesystem error does likewise. The whole scan exits before its group cursor advances or pins clear, then the timer repeats the same group and failure. Healthy sessions later in that group and all later URL groups can starve. Catch and log a per-session error, keep that session eligible for a later retry, and continue the group/rotation; also isolate per-session legacy-link initialization failure. Test a permanently invalid mailbox followed by healthy sessions, including more than one 20-URL group.
2. **A post-commit error can strand notification until a fresh GitHub result.** The watcher records `pendingWake` only when `notifyCommitted` throws, not when `commitPullRequestObservation` throws after the inbox rename succeeded. If subsequent status reads are unavailable, the committed unread event has no same-process wake retry until a fresh status or restart. On ambiguous commit error, queue a wake attempt for the still-valid link while independently retaining the commit retry; a wake with no unread mail is harmless. Test an injected post-rename throw followed by unavailable status and assert one persisted message and a successful retry without another observation.
3. **Running check can go stale before waiter drain.** `mail-delivery.ts:notifyCommittedMail` checks current session/runner under the selection lock once, but awaits `listUndelivered` and `markDelivered` before delivering. `SessionController.stop` calls `runner.stop` outside this lock; it can stop after the check but before marking, allowing a stale long-poll to consume the PR message for a stopped session. The existing test only starts with the session already stopped. Test a gated read/mark interleaving with a real stop. Solve using an explicit shared stop/drain fence or equivalent atomic design; a second unprotected check alone still leaves a window. Preserve ordinary `acceptMail` behavior and lock ordering.
4. **Inconsistent merge fields can create a false closure fact.** `pull-request-status.ts:stateOf` maps a PR to `merged` when either `merged === true` or `state === 'MERGED'`. Contradictory responses such as `{ state: 'OPEN', merged: true }` or `{ state: 'MERGED', merged: false }` therefore produce durable merge mail, despite the contract requiring a confirmed merge and malformed responses to be suppressed. Validate consistent merged fields for the notification observation (without inadvertently breaking public wire compatibility) and test both contradictions.

## Confirmed strengths and verification boundaries

The implementation maintains private link incarnation under the shared pump fence and strips it from wire output, serializes checkpoint and mail in one inbox rename, retains checkpoints through pruning, ignores stale/error rollups, preserves deterministic event IDs and handles normal before/after-rename retry without duplication. Background and foreground use one cache, one flight and bounded pinned group; the status service reserves slots under contention. The 101 focused unit tests and build are reported by W1, not independently run by R2.

The root runtime fixture uses actual status, watcher, controller and MailStore with a fake gh process, but its mail read is an immediate drain. It does not exercise an actual held long-poll/native wake, stopped-agent timing, a bad mailbox alongside healthy agents, real status-service >500/UI churn fairness, or process-kill crash recovery. These paths need targeted runtime/unit evidence as appropriate before claiming them verified. No source changes, tests, runtime, E2E, services or Git operations were performed by R2. Report lease released.

## R2 closure review — further repairs needed

W3 resolves per-mailbox commit isolation, ambiguous-commit wake scheduling and contradictory merge response handling; its targeted tests exercise each. Root explicitly scopes stop behavior to the existing at-most-once handoff: a waiter admitted while running may be marked delivered as the process stops, even if the recipient disconnects before consuming it. This is an acceptable bounded compatibility decision if documented as durable enqueue rather than guaranteed agent processing; already-stopped admission remains unread and no agent is started. Root reports runtime checks including encrypted HTTP long poll, stopped admission and shared-service fairness passed; the full suite remains in progress.

Three concrete starvation paths remain:

1. `pull-request-events.ts` sorts keys via `localeCompare` but seeks the next cursor with `key > cursor`, a different ordering for valid names. For example locale puts `repo_z` before `repo-z`, while code-unit comparison reverses them. With 20 or more underscore names before hyphen names, rotation can cycle only through the underscore names indefinitely. Use the same comparator for sorting and cursor seek; test >20 valid punctuation-mixed URLs.
2. `normalizePullRequestUrl` accepts safe PR numbers larger than 2,147,483,647, but status `entry()` omits them. The watcher still pins such a URL; `group.every` can never find its observation or attempt, so no later group advances. Exclude unsupported numbers from watcher groups or return an explicit non-retryable outcome that advances. Test an oversized link alongside >20 ordinary links.
3. The initial loop that reloads a candidate and lazily initializes its link ID is still not guarded per session. A persistent `loadSession` or `saveSession` failure for one legacy link aborts each scan before any status group can run. Isolate and log that session while continuing healthy ones, and retry it on later scans; test a failed initialization preceding a healthy candidate.

No source, tests, services, runtime or Git actions were performed by R2. Report lease released.

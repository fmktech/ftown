# R1 — independent architecture review

The proposed atomic inbox/checkpoint and shared-status-service approach is appropriate, but the following refinements are needed before implementation freeze.

## Session authority and lock audit

Use one injected per-session `pump.withSessionWrite` critical section for the entire read/revalidate/commit sequence, not merely a URL check or MailStore lock. Capture normalized, case-insensitive URL identity plus a random link incarnation under that same lock. After the asynchronous status read, reenter it, reload and compare session ID, bridge ID, URL key and link ID, then commit the mail/checkpoint while still holding it. Unlink/relink A→A must mint a new ID; a case-only spelling change of the same normalized GitHub owner/repo and PR number must not. No mkdir in the event commit. Deliver/wake only after releasing this lock. The lock order is pump session mutation → mail file lock, then release before the delivery selection lock; ordinary delivery uses selection → mail lock and must never acquire pump from within either, avoiding inversion.

Audit of actual production save/remove paths, rather than assuming the SessionStore's independent internal write lock protects a read-modify-write:

- `SessionController.update`, `remove`, `retry`, `usage` and preview mutators use its `withSessionMutation` wrapper (`session-controller.ts:205–220`, `296–338`); `stop` uses injected `withSessionWrite` (`:108–120`). Normal `index.ts:853–862` injects the pump lock for the shared controller and `removeFtownSession` calls `deleteSession` through it.
- `terminal-pump.ts:145–165, 167–179, 216–229` reloads and saves under that same lock. `session-ids.ts:120` and `hook-usage.ts:68` do full-snapshot saves, but normal callers wrap the entire pair in `pump.withSessionWrite` (`index.ts:961–966`). `session-resurrection.ts:50,71` and `relaunchFtownSession` at `create-ftown-session.ts:364` are called under the injected lock by resurrection and retry (`session-resurrection.ts` resurrection loop and `session-controller.ts` retry). Keep those invocation guarantees. Initial `create-ftown-session.ts:473` saves a newly minted UUID before any link exists; archive revival creates a new UUID and does not copy the association.
- `SessionStore.saveSession`/`deleteSession` have a *different*, private per-directory lock and serialize individual writes only, not earlier snapshot reads. Direct use from another runtime/controller would bypass the fencing. `LocalApiServer.getSessionController` fallback constructs a separate controller without injected pump lock (`local-api-server.ts:372–384`). Root chose the bounded contract: start watcher only in normal `index.ts` after the actual shared controller/pump is wired; standalone fallback has no watcher. Test fixture must inject the identical lock into both watcher and controller. Do not broaden alternate constructors in this task. Never add a raw `removeFtownSession` or `deleteSession` caller bypassing the lock.
- Add the field only as private persistence metadata: `session-wire.ts` currently strips only `env` and `previewSource`; explicitly strip `pullRequestLinkId` there for HTTP, RPC and Centrifugo publication. Cover this in wire tests.

`saveSession` publishes `session.json` through temp+rename but does not fsync (`session-store.ts:66–83`). For a claim of crash/power-loss-durable incarnation fencing, link/clear and lazy legacy-ID updates must durably fsync the file and parent directory before acknowledging and before watcher use; otherwise narrow the guarantee to process crash only. Test old link snapshot held across update, concurrent hook/usage/terminal/resurrection saves, unlink/relink and removal during gh fetch, and no write after deletion. Session removal and stop must not cause a late delivery to recreate a directory or revive a stopped agent. `runner.stop` happens before its lock (`session-controller.ts:108`); recheck runner and session liveness in notification before any wake.

## Inbox atomicity and recovery

Use a single same-directory atomic rewrite of the mailbox under its existing per-session mail lock, with a versioned tagged checkpoint and ordinary new mail in the same snapshot. `readAll` currently ignores anything without message id/body and `markDelivered` rewrites only its parsed messages (`mail-store.ts:43–106`): every writer/rewriter must preserve and validate the checkpoint, preserve existing legitimate mail, and prune only delivered messages. Do not treat a replayed terminal state as a new event because the corresponding delivered mail was pruned. A deterministic event ID derived from incarnation and a durably incremented transition ordinal keeps retries stable; persist no-mail `in_progress` observations as well. Serialize with all normal append/delivery operations, and do not count the checkpoint toward the 500-message cap. An invalid or duplicate recognizable checkpoint must fail closed; do not silently discard it during read/prune. Preserve or explicitly handle older corrupt ordinary lines consistently with legacy policy.

Atomic temp write, file fsync, rename, and directory fsync give a complete old-or-new snapshot in the modeled process/crash sequence. A failure *after* rename is an ambiguous commit: reload/validate the current snapshot and retry durability/wake using the same checkpoint/ID, never assume no commit or generate a second event. Fault-inject before/after rename and fsync; exercise >500 delivered messages, concurrent ordinary append and `markDelivered`, unread retention, and restart. No inbox-only scheme can distinguish a missing checkpoint from a never-initialized legacy inbox in every external deletion/truncation scenario. Either establish a separately durable initialized marker with explicitly crash-tested ordering or honestly limit the corruption guarantee: reject malformed recognized records, do not claim undetectable total marker loss is caught.

Call a post-commit selection/waiter/nudge method after releasing the session lock, without calling `acceptMail` again. A crash after commit and before notification relies on existing recovery for running sessions; same-process wake failure must be retried for already committed unread mail even if the next observation is a duplicate. Long-poll delivery must preserve `withSelection`/`available`/`markDelivered` semantics and checks for waiter abandonment. No exactly-once end-to-end wake claim: side effects and delivery marking can fail or be replayed; durable idempotent *enqueue* is the scope. Stopped/removed agents are never started.

## Status, ordering and quota

Keep one shared status cache, runner, flight, cooldown and quota for both UI and watcher. Require fully validated fresh current-head rollup for failed/passed/in-progress and a confirmed merged state for merge; no old head on stale, error, mismatch or malformed response. Unknown/error/no-check/closed must not overwrite known transition state. Use one single-flight watcher, serialize observation commits per link, and deduplicate by link + head + state/transition ordinal; wall-clock `checkedAt` alone is not a reliable order/replay key (clock ties and regressions). A → pending → A may emit again only after a distinct fresh observed transition. State can change and return between polls: guarantee observed transitions, not every remote transition.

`get()` caps cache at 500, selects at most 20 aliases, and admits one launch/minute. Merely rotating input batches of 500 does not establish >500 fairness; in particular an active UI can consume each available launch, and calls can evict entries that an in-flight refresh is updating. Freeze a bounded fair admission policy shared by both sources (e.g. alternating foreground/background when both have queued work, rotating stable background chunks of at most 20), preserving quota/cooldown and allowing UI to return cached status while waiting. Pin or serialize in-flight cache entries so an intervening large UI request cannot evict and lose the fetched result; maintain the 500-entry bound. Guarantee eventual background progress only while GitHub/auth/quota permit; test >500 distinct URLs, competing UI calls, cache eviction/flight, identical shared URLs, cooldown, empty/malformed responses, shutdown and >20 batches. If no fair admission is implemented, explicitly weaken and document the fairness claim.

## Product semantics and acceptance

Mail states are facts at `checkedAt`, include canonical PR URL, current observed head for checks and a checks link, and say GitHub rollup rather than required checks. Never interpret mail as push/merge permission. Choose explicit shell behavior (skip plain shell is a safe conservative option), but stopped agent records can retain mail without launching. Test two agents sharing one URL, initial terminal state, new head, distinct rerun transitions, merge once, stale/error suppression, power/process crash points, >500 pruning, failure after commit before wake, liveness and deletion fences. Runtime validation belongs to root: actual MailStore/watcher/delivery, temporary session data, fake gh executable and no network.

These are freeze recommendations; no application source, runtime, E2E, Git, or service actions were performed by R1. Report lease released.

## Root scope decisions and bounded fairness refinement

Root narrows crash durability to process restart/crash with an atomic same-file checkpoint and message. Power loss, external deletion and arbitrary unrecognized corruption are outside the claim; malformed/duplicate recognized metadata remains fail-closed and legacy mail semantics remain. SessionStore fsync redesign is not needed for this scoped guarantee. Watcher starts only in the normal shared-pump runtime, and `toWireSession` strips the private link ID.

A small status-service change can meet the bounded fairness requirement without a global queue: watcher registers and pins one stable group of at most 20 canonical URLs in the existing <=500-entry cache; reserve at least one alias slot for a due pending watcher entry whenever foreground and background are both due, and at least one for due foreground, then fill remaining slots using existing ordering. A foreground call can perform this same shared flight, and the watcher holds its group when cooldown/quota prevents an actual attempt. Internal monotonically increasing per-attempt ordinals distinguish a real alias attempt, including failure, from a cached/blocked return; after every group item has either a usable fresh cached observation or a real attempt, rotate in stable URL order, retrying failed aliases on a later rotation under existing cooldown. Pin pending and in-flight entries against LRU eviction and evict unpinned only; count all toward 500. An ordinal is internal and does not alter UI protocol. A reservation is necessary: sorting solely by `lastAttempt, used` can starve a pinned stale watcher entry with nonzero lastAttempt if UI continuously inserts new zero-attempt entries. Fair progress depends on a live bridge and quota/auth permitting launches; preserve the single global flight and 20-alias/minute gate. Root test should exercise continuous distinct UI churn with >500 background URLs, same URL sharing, eviction and alias failure/cooldown.

# D1 — PR agent events design findings

## Existing boundaries

- `bridge/src/pull-request-status.ts` already has one `PullRequestStatusService`, instantiated once in `bridge/src/index.ts:869` and passed to `createCommandHandler`. `get(urls)` normalizes/de-duplicates URLs, shares a process-wide in-flight request and one launch/minute, max 60/hour, <=20 aliases/query, cache <=500, auth/rate cooldown, and 1m/5m/1h/forever TTL by state. It fetches `headRefOid` and verifies `commits(last:1).nodes[0].commit.oid` equals that head before mapping rollup, but throws away that head. It aggregates GitHub rollup with `contexts.totalCount`, not required-check policy. `unknown/no_checks`, stale, malformed, unavailable, authentication/rate-limit and GraphQL alias errors are not terminal results. Merged is cached forever; current parser accepts `merged` before validating head.
- Local and dashboard PR updates go through `SessionController.update` (`session-controller.ts:205`) and its per-session mutation wrapper; removal goes through that wrapper too. In normal `index.ts` this uses `pump.withSessionWrite`, while `SessionStore` has a distinct private per-session directory-write lock (`session-store.ts:52`). Watcher must use the *same controller/pump mutation lock*, not just its own lock or an earlier `loadSession` check. `MailStore.append` does its own `mkdir` and has a separate per-session lock; a naked watcher `loadSession` then `append` can race deletion and recreate a removed directory. `Session` currently persists `pullRequestUrl` but no link incarnation, so URL equality alone cannot fence A→clear→A while a gh call is pending.
- `MailStore` `inbox.jsonl` has per-session serialization; `markDelivered` atomically rewrites but drops oldest delivered messages above 500. Neither `append` nor `createMailMessage` is idempotent; scan of message history is insufficient after pruning. `MailDeliveryService.acceptMail` appends and under `withSelection` wakes a waiting hook or schedules native/legacy nudge; `recoverPendingMail` only wakes running sessions and does not auto-start stopped sessions. A background producer cannot safely call existing `acceptMail` after an independent checkpoint write without handling its crash boundary.
- `bridge/skills/ftown/SKILL.md` documents PR association but no automatic events. `bridge/AGENTS.md` requires patch version bump and matching lockfile for bridge runtime/shipped skill changes.

## Recommended frozen interfaces and semantics

1. **Current-head snapshot without UI wire change**: in `pull-request-status.ts`, maintain internally `headOid?: string` alongside cached status, and expose `getObservations(urls: readonly string[]): Promise<{ observations: PullRequestObservation[]; nextRefreshAt: string }>` where `PullRequestObservation = { url: string; state: PullRequestState; checkedAt: string | null; stale: boolean; reason?: PullRequestStatusReason; headOid?: string }`. Have both public `get()` and internal method use the *same* cache, `flight`, fairness, quota and gh runner; public `get` explicitly projects existing wire shape. For `failed/passed/in_progress` require a valid nonempty OID from the exact validated current-head commit, never reuse an old head on unavailable/stale/mismatched response. For `merged`, stable canonical PR URL + link incarnation identifies its one merge; validate the returned PR's merged flag/state. Optionally query/validate `mergedAt` for a useful timestamp; do not require `mergeCommit` (nullable). Status snapshots mean last successfully observed rollup at `checkedAt`; GitHub can change head immediately after observation, so include head and observation time in mail and do not claim real-time certainty.
2. **Link incarnation and fencing**: add bridge-persisted optional `pullRequestLinkId?: string` to `Session` (`types.ts`), generated with `randomUUID()` in the same metadata update as a changed/cleared-and-relinked PR. Canonical same URL update preserves it; removing/clearing deletes it. On startup, lazily initialize missing IDs for legacy associated sessions under the same shared session mutation lock, reloading before saving. Each watcher scan captures `{sessionId, normalizedUrl, linkId}` before gh; after fetch re-enter that lock, reload and require exact session existence, matching canonical URL + link ID and same bridge before any state/mail write. This fences stale fetch A→B, A→clear→A and deletion; never call `mkdir` from event commit. Ensure all live unlink/removal entrypoints use the same lock (normal index already routes through one controller); explicitly test direct lifecycle/removal paths and avoid assuming `SessionStore`'s separate directory lock is equivalent. Avoid exposing the link token in UI protocol if possible. Existing non-controller writers that save stale full session snapshots can overwrite this token: integration review must audit session save paths or use a distinct link-generation authority that cannot be clobbered; lock correctness is a gate, not implied by rereading the URL.
3. **Atomic inbox event + durable cursor**: add one purpose-specific `MailStore` operation, e.g. `commitPullRequestObservation(sessionId: string, linkId: string, observation: FreshObservation): Promise<{ enqueued: boolean; messageId?: string }>` while caller holds the shared session mutation lock. Serialize with existing mail per-session lock. Represent one versioned PR observation checkpoint record in `inbox.jsonl` alongside ordinary messages (a tagged metadata line ignored by normal inbox read). Atomically rewrite this one file via same-directory temp + rename, including both updated checkpoint and new ordinary `MailMessage` in the same snapshot; preserve checkpoint through `markDelivered` pruning, legacy inbox entries and all concurrent regular `append`/delivery operations. Never use `mkdir` in this path. Use owner-only permissions, fsync file and parent directory for crash durability; invalid/corrupt checkpoint must fail closed and retry/diagnose, never discard an unreadable marker and manufacture duplicates. Ensure reader keeps checkpoint private and never exposes it as agent mail. Existing cap applies only to delivered messages; the single checkpoint is bounded independently. New link replaces its checkpoint under validated incarnation.
   - State machine persisted per link: initial fresh terminal `failed`, `passed`, `merged` emits once; `in_progress` persists to support reruns without mail; `closed`, `unknown`, stale/error/rate-limited do not emit (unknown/error must not overwrite last known transition); new head resets head-specific state. On same head, `failed→in_progress→failed`, `passed→in_progress→passed`, and `failed↔passed` are new transitions and each yields one message. Repeated same state/head or replayed same `checkedAt` yields none; merged is terminal once per incarnation. Different heads with the same state each emit. Persist observation time/monotonic transition ordinal; deterministic message ID based on link incarnation + ordinal + state + head (merge keyed on link + merged fact). Since cursor and message land in the same rename, crash before rename leaves neither, crash after rename leaves both; no external cursor-write window and no dependence on old delivered messages. Restart scanning obtains new observation and respects persisted state even after >500 delivered messages. Partial/corrupt journal or failed write must not silently advance state. Explicitly decide and test fsync/rename error behavior; a success response before durable fsync would weaken crash guarantees.
4. **Wake existing delivery without second append**: extract a post-commit method from `MailDeliveryService.acceptMail`, e.g. `notifyCommittedMail(session: Session, sender: string): Promise<void>`, retaining `withSelection`, long-poll draining, `markDelivered`, native wake/nudge and running checks. `acceptMail` continues validating and appending exactly once then invokes same logic; watcher calls it only after atomic commit, *outside* session mutation lock if it cannot create mail (avoid lock inversion), and rechecks process/session state in existing wake path. If a crash occurs after commit but before notification, `startMailRecovery`/`recoverPendingMail` re-arms unread mail for running sessions on restart; if a post-commit wake fails within the same process, retry the wake on subsequent scans without reappending. Stopped sessions retain mailbox records but are never started/resurrected. Verify long-poll waiters are notified too: `recoverPendingMail` alone only schedules a nudge and is not equivalent to `acceptMail`.
5. **Background lifecycle**: new `bridge/src/pull-request-events.ts` exports a bounded single-flight `PullRequestEventWatcher` with injected `{ listSessions, withSessionMutation, statusService, mailStore, notifyCommitted, now, setTimeout, clearTimeout }`, `start(): void`, `stop(): Promise<void>` or equivalent awaitable shutdown; default on explicit association, no UI/browser required. Use fair rotating session/URL collection with a bounded maximum of <=500 per cycle, `getObservations` batched by the existing 20-url/quota service, and schedule at or after `nextRefreshAt` with >=60s floor. No independent gh process, retries/force-refresh or quota bypass; share URL fetch across sessions. Ensure starvation-free handling of >500 URLs, stop timers, drain/fence an in-flight fetch on shutdown, and avoid resurrecting removed dirs. All session states with explicit PR association can accumulate mail; existing delivery only nudges a live agent. For plain `shell` decide explicitly whether to skip (it cannot autonomously handle mail); do not silently claim a wake caused a stopped agent to run.
6. **Mail copy/skill**: `from: 'external'`, `fromName: 'FTown PR updates'`, `type: 'message'`, neutral factual body with canonical URL, checked-at and head on CI states, plus canonical `/checks` link. Failure directs inspect and reproduce before retry; success says rollup checks passed and follow existing task/user rules; merged reports merge and follow completion instructions. Never say all *required* checks passed, claim a status came from current HEAD beyond observation, send automatic merge/push authorization, or ingest untrusted CI logs. Extend `bridge/skills/ftown/SKILL.md` PR section explaining opt-in-by-association, availability/staleness and durable mail semantics.

## Writable files, dependencies and checks

Likely product paths: `bridge/src/pull-request-status.ts` + its tests; `bridge/src/pull-request-events.ts` and new unit tests; `bridge/src/types.ts`, `bridge/src/session-controller.ts` + tests for link incarnation; `bridge/src/mail-store.ts` + tests for atomic inbox/checkpoint/pruning/restart; `bridge/src/mail-delivery.ts` + tests for postcommit waiter/nudge/recovery; `bridge/src/index.ts` lifecycle; `bridge/skills/ftown/SKILL.md`; `bridge/package.json` and `bridge/package-lock.json` patch version. Depending on audit, `session-store.ts`/tests or shared mutation seam may need a narrowly scoped change to fence all directory mutations and stale session snapshots; settle before contract freeze. No public status protocol or UI change required. Treat these as one writer wave or explicitly disjoint ownership with a frozen shared contract; root is integration/E2E owner.

Key acceptance: exact current-head and mismatch/stale suppression; initial terminal; rerun transitions and new head; merged once; two sessions same URL; batched fairness and cache cooldown/quota shared with UI; crash at before/after rename and after commit/before wake; >500 delivered pruning; old inbox compatibility; stale in-flight unlink/replace/remove/A→clear→A and stop races; live native/long-poll wake exactly once and stopped session no resurrection; non-agent shell decision. Root-only runtime: task-local scratch `HOME`, bridge data dir, ephemeral listeners, fixture `gh` executable in private PATH returning scripted GraphQL JSON (no real GitHub/network or live user sessions), actual watcher + MailStore + delivery and restart. Exercise create/link → head failure → rerun pending/success → merge, no dashboard, restart/no duplicate, unlink/remove in-flight, stopped no wake. Service/process ownership and cleanup root-controlled.

Relevant existing focused tests: `cd bridge && node --import tsx --test src/pull-request-status.test.ts src/session-controller.test.ts src/mail-store.test.ts src/mail-delivery.test.ts` plus new watcher tests and `npm run build`; check exact available filenames before invoking. Full required bridge gate per repo; Node engines `^22.23.4 || ^24.22.1 || >=26.12.1`. Root owns all runtime/E2E. No live gh calls, services, installs, code edits or Git operations performed in D1.

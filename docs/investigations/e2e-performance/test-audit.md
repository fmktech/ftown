## Authentication and capacity budgets

Do not disable limits to make the concurrent run pass. Pair start is the tight shared resource: **20 per client IP/hour** (`ui/src/app/api/auth/bridge/pair/start/route.ts:25–30,65–73`). The current browser inventory starts **12 virgin bridges** (account 6 + pending 5 + device pairing 1), below this cap in a fresh run; seeded harness bridges use their prearranged onboarding. Parallelism changes scheduling, not that count. **Two complete runs against the same limiter state can exceed 20; repetitions need fresh isolated DB/environment, not limiter-row deletion or weaker limits.**

Pair approval is per email 30/10 min (`pair/approve/route.ts:20–25,35–43`), polling per device code 200/10 min (`pair/poll/route.ts:47–52,69–73`). Successful credentials reset failed-login email/IP counters and do not consume a failed-attempt pool (`ui/src/lib/auth.ts:63–81`). Browser pending reads/mutations use owner-scoped 200/60 per minute (`pending-approval-http.ts:12–17`; `account/_shared.ts:33–50`), so separate case owners do not collide. Pending candidate calls have a shared-IP 600/minute cap (`pending-approval-http.ts:43–50`); the two-worker schedule does not add protocol polls, but runtime should still check for 429s and retained stuck requests. Pending quotas are 128 per target/4096 global with 5-minute lifetime and 2-second cadence (`bridge/src/security/pending-approval-crypto.ts:16–20`); current few test-owned requests are well below capacity. There is no measured per-minute request histogram yet.

# Native mail delivery

Status: frozen v1, 2026-10-18. Independent pre-freeze review by /root/npx_review accepted wake-only design. Exact endpoint shape incorporates /root/npx_implementation review.

## Behavior

The existing durable inbox remains the only message queue. New native adapters submit a short instruction to read `ftown harness mail read`; they never send the message body or mark mail delivered. This preserves existing mail commands, hooks, routing and MCP behavior. An accepted wake means queued/started, not message consumption or task completion.

Prefer native wake for Codex queue, Muse session-message (only with verified admission semantics), Claude Mods and the OpenCode plugin. Pi retains its existing native follow-up extension. Cursor, Grok, Kimi Code and older/unsupported clients retain legacy delivery. Do not change runtime ownership to ACP/MSP servers in this task.

## Native command boundary

`bridge/src/native-mail.ts` exports `NativeMailWakeResult` with `status: 'accepted' | 'unsupported' | 'rejected' | 'unknown'`, `NativeMailWaker = (session: Session, text: string) => Promise<NativeMailWakeResult>`, and `createNativeMailWaker()` with optional dependency injection for tests. Core imports the factory and type. Return unsupported for other harnesses, absent/invalid native UUIDs, missing executable or unsupported command. Probe command support without model calls, cache bounded probe results, and execute argv with shell disabled. Muse body goes through stdin. Bound execution/output and avoid logging bodies/credentials.

Accepted and unknown outcomes never trigger an immediate PTY fallback. Rejected permits fallback only when the adapter can prove no native submission was accepted. Unknown includes post-spawn timeout, malformed receipt and unclassified command failure. Preserve busy deferral and rate limits for PTY. Native commands may queue while busy. Recheck session existence, running state, pending mail and cancellation before side effects; serialize wakes per session. Existing scheduled work must stop on bridge shutdown.

Approved boundary amendment: `NativeMailWaker` may accept optional third `AbortSignal` and optional fourth `isCurrent: () => Promise<boolean>` for shutdown cancellation and final revalidation after asynchronous capability probes. Existing two-argument callers remain compatible. Adapter matches target session environment/cwd, strips inherited sender identities and avoids accidentally targeting the current agent's transport.

## Plugin heartbeat

Authenticated `GET /api/sessions/:id/inbox?peek=1&wait=0&adapter=claude-mod|opencode&nativeSessionId=ID` preserves `{messages}`. Both adapter/identity fields are required together. Malformed registration returns 400; mismatched/unresolved identity, wrong harness or stopped runtime returns 409. Claude accepts its four provider aliases. Validate native identity against the session's recorded claudeSessionId/opencodeSessionId and the live runner. No workspace-derived attribution. Existing peeks without these fields remain unchanged.

Successful requests refresh an in-memory native wake lease for 30 seconds. Plugins poll every 5 seconds. The lease suppresses PTY nudges, including previously scheduled ones; expiry restores the existing fallback. Heartbeats continue while prompt submission is pending. Session identity is rechecked before suppression; session removal/bridge shutdown invalidates state. Plugins never drain the inbox.

Claude Mod submits an attributed wake via `$.prompt.submit`, outside blocking turn hooks, with one submission in flight and unread-ID tracking to avoid repeat wakes for the same unread mail. Dropped prompts may retry with bounded backoff; unknown outcomes must not spin or immediately duplicate. Polling re-reads native identity, fences stale callbacks across clear/resume/reload, and reconnects using the bridge pointer after restart. Manual non-FTown runs are inert. Keep classic status/mail hooks for compatibility. Install Mod assets through setup and load only compatible Claude versions, including provider aliases; startup remains read-only.

Approved launch amendment: existing UI builds an explicit default Claude command, bypassing registry generation. Centrally recognize only the exact legacy default/resume command generated by FTown and route it through the canonical builder so existing/cached panels receive the Mod. Preserve genuinely custom commands verbatim. Claude worker owns agent-commands.ts and its test for this narrow compatibility fix; no UI changes.

OpenCode uses its existing native client to submit the same wake instruction, with independent periodic inbox polling to wake an idle session. One submission in flight and unread-ID suppression. Never run the previous unrestricted drain after a prompt: it could consume mail that arrived during that prompt. Preserve lifecycle forwarding and avoid submitting into the wrong/subagent session.

## Acceptance and limits

Unit checks cover native selection, exact UUID/argv/stdin, definite rejection vs unknown, unsupported fallback, busy native queuing, stale/mismatched heartbeat, stop fencing, no PTY with healthy plugin, recovery after expiry, plugin rejection/retry/lifecycle and concurrent arrivals. Existing mail API/CLI tests remain passing. No assertion of exactly-once wake or work completion; mailbox read/disconnect behavior is unchanged.

Root executes focused runtime/E2E against isolated HOME/workspace/processes, no production sessions or database. Verify packaged setup/copy, live local bridge mail send/read and required `ftown harness status`; validate Claude Mod with installed CLI and test native Codex/Muse where feasible. A client whose admission cannot be verified stays on fallback and is explicitly documented. Integration owner bumps bridge patch version, runs build and checks, commits only task files, pushes and opens PR. Root does not merge.

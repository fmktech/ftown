## Product and acceptance

- One approval connects a new bridge and establishes its encryption trust. First approval also creates the first account device when the account has no trust history.
- One approval enrolls each browser installation for all current and future account bridges. Each browser keeps separate nonextractable HPKE and ECDSA keys. Logging in alone does not authorize keys.
- Existing trusted browser approves a fresh phone/browser using a short-lived link with a fragment secret and a comparison code. No terminal contents before approval. The secret never enters an HTTP request or log.
- MCP keeps its existing encrypted, exact-bridge, read/control, fixed-expiry grant receipts. One consent obtains all selected receipts automatically through account-trusted browser access. Selected bridges must be online; future bridges are excluded. No second MCP pairing step, no account signing authority for the gateway.
- Security Devices shows the account device list, this device, and account revoke. Explain trusted browsers can control account computers and approve other devices. Activity retains its bridge filter. Mobile controls >=44px; pending/expired/offline/revoked states are distinct.
- Preserve Solo and OS-local recovery, legacy bridge encrypted access until explicit migration, existing MCP grants, encrypted transport and audited actions.

## Trust model and decisions

Use a flat signed roster. A genesis names owner UUID, random 256-bit root ID, and initial browser endpoint/signing key. Genesis signature proves the initial signing key but is not authority until pinned via a trusted local/browser bootstrap. A transition contains exact owner/root, previous payload hash, next revision, signer endpoint, timestamp and one typed operation. The signer MUST be an active device in the previous verified state. Any active device is an administrator. No delegated certificate ancestry.

Separate ECDSA P-256/SHA-256 keys sign; existing ECDH HPKE keys encrypt. Strict schemas reject unknown fields and malformed/noncanonical base64url, oversized input, non-integer revisions, mismatched owners/kinds, key fingerprints, duplicate additions, invalid times or key points. Canonical bytes are UTF-8 JSON with recursively sorted object keys, original array order, no undefined/nonfinite numbers, and a domain prefix `ftown-account-trust-v1\n`. Sign and hash the same canonical payload bytes; hashes do not include ECDSA signatures. WebCrypto signatures are canonical unpadded base64url of 64-byte P1363 output. Roster derived arrays are sorted by endpoint ID/bridge ID. Devices/bridges remain bounded; removed IDs are permanent tombstones. Last-device revocation is rejected. Existing devices cannot be re-added with changed keys, and a revoked bridge ID needs a newly registered ID.

Exact device revocation does not cascade to independently approved devices or previously activated MCP grants. A compromised admin could approve another device before its own removal; the list makes those approvals visible. Server cannot forge a device approval but provides CAS ordering and delivery of latest history. Persist genesis/root, accepted revision/head, derived state and local last-read timestamp atomically. A valid response must contain the pinned prefix/head and full verified continuation; known rollback or conflicting history fails closed. Empty history never resets a pinned account.

The 24-hour offline grace measures connectivity, NOT a guaranteed revocation deadline. Renew it only after a successful authenticated HTTPS account read whose complete signed history matches/extends the pin. Invalid/older/conflicting responses do not renew it. A malicious service can withhold updates or fork old history with a stale compromised admin; this design is not Byzantine consensus and does not claim globally instantaneous revocation. Honest service delivery lets clients/bridges learn changes within the 30-second refresh interval. After 24 hours without a valid read, account-derived access stops; local recovery and independent fixed-expiry MCP policies retain their existing rules. Track lastObservedAt alongside lastServerReadAt, persist them atomically with trust and on clean shutdown, reject observed backward wall-clock movement, and use monotonic elapsed time within the process so rollback to a value after the last read cannot extend access. After process restart require a valid authenticated history refresh before granting account-derived access; this avoids claiming trustworthy elapsed downtime from an adjustable local clock. Local recovery remains available. Never decrease persisted highwaters on a later read. A startup network failure is distinct from running-process24h offline grace.

Full history is limited to 1024 transitions / 2 MiB; no heartbeat events. Fetch and verify against the durable pin; the first bootstrap packet authenticates an AccountHead; full matching public history is fetched separately and derives the checkpoint. No unsigned checkpoint replacement or silent pruning. Capacity errors are explicit, with recovery/rotation outside this change. All signing private keys stay on browsers. Gateway private keys retain existing encryption at rest.

## Bootstrap and enrollment

Candidate generates a 256-bit secret, challenge and request ID, and five-minute expiry. Request includes exact HPKE endpoint, kind, label; browser also includes its independent signing key and a signature over the request excluding signingProof using domain `ftown-account-enrollment-v1\n`. Bridge pre-auth candidate owner is `pending:<bridgeId>` and becomes the authenticated UUID only inside the approved transcript; the public point/fingerprint is unchanged. Browser owner must already equal authenticated UUID. Candidate saves keys/secret locally for the request lifetime. Bridge pending material uses existing atomic 0600 storage. Generate pending keys only for virgin bridges; existing bridge reauthentication preserves its bound key/root and uses the existing auth-only flow or explicit migration, never replaces it. The neutral generateAccountBridgeCandidate/importAccountBridgeCandidate helpers produce/restore this pre-auth key without widening ordinary crypto owner validation; normalize only inside approved bootstrap.

Only a fragment link transfers the secret. The fragment field is account=<base64url UTF-8 JSON AccountEnrollmentLink>; parseAccountEnrollmentLink accepts that encoded string or a strict parsed object. Links use /pair?code=<public userCode>#account=... or /devices/approve#account=.... The public-request parser separately validates signingProof without needing the secret. Comparison code is SHA-256 of domain ftown-account-comparison-v1 plus newline plus canonical {request,secret}, first12 uppercase hex digits displayed as three groups of4. Parse the fragment client-side, immediately remove it from visible history, retain only in per-tab memory/session storage for login continuation, and never put it in next/returnTo/search parameters, analytics, errors, referers or server logs. Local login continuation supports bounded same-origin `/pair` and `/devices/approve` paths in addition to MCP; reject arbitrary redirects.

Trusted approver validates exact link/request and browser signing proof, refreshes pinned history, explicitly confirms device/computer, signs the typed addition, appends via CAS, then produces an HPKE Auth encrypted bundle for the exact candidate key. Bundle plaintext binds request, owner/root, exact AccountHead, approver key, approvedAt and expiry with HMAC-SHA256 keyed by the fragment secret. HMAC input is the canonical plaintext excluding secretProof plus the exact approver endpoint, domain `ftown-account-bootstrap-v1\n`. Envelope purpose is existing `enrolled`; channel `account-enrollment:<requestId>`; bridgeId is requested bridge ID or `account_<ownerId>` for browser. Normalize pending bridge endpoint owner only to bundle owner. Receiver epoch null. Existing envelope age rules apply: issue <=120-second response envelopes while enrollment itself is valid; retry may reseal the same approved membership.

Candidate fetches public history separately over authenticated HTTPS, opens with its HPKE key, validates HMAC and complete transcript/history, validates exact membership/key(s), derives the checkpoint at the authenticated bundled head and validates approver was active there (not necessarily still active in a later continuation), then atomically persists trust before any application access. Neutral openAccountApproval returns VerifiedAccountTrust without a freshness timestamp; only the caller that performed the authenticated matching account GET can set lastServerReadAt. History may extend the authenticated checkpoint; candidate must remain active in the verified latest result. A bridge obtains the current history with its newly issued owner token before starting account access. Decryption proves candidate HPKE possession; browser request signature proves signing-key possession. Server cannot substitute a candidate key or inject approval without fragment possession. Approval alone may leave an unusable roster entry if candidate never finishes; do not claim active connection until encrypted handshake succeeds.

First-account browser authority pinning/activation is allowed ONLY during explicit new-bridge approval or explicit migration through an existing pinned bridge administrator. The account API may store an internally valid genesis for its authenticated owner before that action; storing a self-signed public record confers no bridge/client authority. Only trusted bootstrap pins it. API null does not mean a known/pinned account is new. A fresh browser on an established account must be approved first, even if it is adding a new bridge. A malicious service could lie about an unpinned account to a virgin bridge and create an isolated root; established clients reject that root and are never reset.

## Shared seams and API

All components import types from account-protocol. Pure named exports in account-crypto implement AccountCrypto and export ACCOUNT_TRUST_LIMITS; they import existing neutral crypto but no Node/server/UI modules. Browser/server/bridge may import neutral core. Core is implemented and independently reviewed before dependent application writers start.

- `GET /api/security/account` returns AccountReadResponse. Owner from browser session or existing bridge bearer subject mapped to immutable UUID; never body owner. Public material only. Empty is null.
- `POST /api/security/account` accepts AccountAppendRequest, same-origin browser auth required. Server independently validates signature/history, owner, exact expected head and bounds; first genesis insert only if no row. Transaction/CAS yields 409 conflict; caller refetches, verifies and re-signs after reconsidering state (no blind stale replay). Returns AccountReadResponse.
- `POST /api/security/account/enrollments` returns AccountEnrollmentStatus and creates AccountEnrollmentRequest for authenticated browser owner. Bridge enrollment travels existing pair/start instead. Never accepts the secret. Strict body/TTL/rate bounds; pending rows expire and are cleaned. Request ID collision cannot replace data.
- `GET /api/security/account/enrollments/<id>` returns AccountEnrollmentStatus, owner-only, no-store. `POST` same path accepts AccountEnrollmentApproval, bound exact request/owner, public bundle recipient/owner/request bindings must match the stored candidate and current signed membership; server cannot inspect plaintext or verify the secret HMAC, permits resealing an already-approved request while still within its five-minute expiry: same request, owner, candidate and approver, with a fresh encrypted envelope and matching approved membership; it never adds membership a second time. Encrypted head/HMAC remains authoritative at the candidate. Authenticated server validates available wrapper bindings; ciphertext is not an API authorization proof. This supports resuming after the first120-second response expires. Approval POST also returns AccountEnrollmentStatus. Pending/approved polling; candidate treats ciphertext as untrusted until verified. Expiry410; no pending request enumeration by unauthorized account.
- Existing pair/start adds `enrollment`; lookup includes enrollment: AccountEnrollmentRequest|null (null is legacy); approve takes `accountApproval`; poll returns `accountApproval` and public `accountHistory` alongside existing credentials. Require matching bridge ID, request and candidate; old clients may continue old ownership registration (never receive account authority). New UI does not silently downgrade if new binding is missing. Validate before consume; expired consumed request cannot issue credentials. Browser one-click append+approval may leave signed orphan membership on a network failure; retry same exact membership/request safely, no hidden automatic additional additions.
- Browser `account-security-client.ts` owns HTTP/state orchestration; `useAccountSecurity` exposes checking/unapproved/ready/error and stored trust to UI. Browser identity storage persists signing key pair, pinned trust, enrollment continuation, and retains separate local bridge pins. `useBrowserIdentity`/runtime derive account bridge pins only from verified roster and keep legacy/local routes functional. Unverified directory remains discovery only.
- Bridges fetch account history on startup and every30s with their owner-authenticated credentials; apply only to pinned account. New bridge pins via verified pairing bundle. Existing bridge uses admin encrypted `security_account_adopt` command with AccountHead; it fetches public history from its configured owner-authenticated API and requires the exact requested head, so large histories never enter a450000-byte command envelope. It validates actor is an active prior bridge-local browser administrator, actor exact HPKE endpoint is an active device in the derived account, same owner and bridge exact key are present, and revalidates the actor immediately before atomic installation. A changed server head returns conflict for verified browser retry. Actor approval of the exact root/head via the existing pinned encrypted connection is the trust witness; a database snapshot alone is insufficient. The prior bridge-local admin already has authority to choose that bridge trust root. This is an explicit authenticated root-install operation, not an inference of ECDSA possession from the latest log signer; the actor need not author the latest/add-bridge record, but must be an active exact-key device in the chosen roster. Server cannot replace the head inside that HPKE command. Already pinned bridges never replace root through this command; same-root continuity allowed. No adoption via plain public directory.
- `BridgeSecurity.adoptAccount(actor, head)` returns AccountHead. New command `security_account_adopt {bridgeId, head}`; result `{head}`. Worker bridge owns permission-map dispatch. Internal startup/poll apply persists trust, increments policy generation and closes revoked peers; all admission, publications, responses and queued work check latest policy and grace. No need to add account proof to every wire envelope: newly approved devices wait for bridge refresh before authenticated hello succeeds.

## Migration and recovery

Existing bridge trust stays usable until adopted. A legacy trusted browser offers one clear “Use account device approvals” action: establish or refresh account, add exact pinned bridge, and send encrypted adoption. Once adopted, atomically clear legacy browser grants AND all outstanding legacy invitations and use current account membership; preserve local CLI and existing MCP grants. Account pin, member projection, browser-grant removal and invitation invalidation must share one AtomicSnapshot transaction/file; corrupt or failed loading must fail closed, never fall back to old browser policy. Other legacy browser installations require one account approval. After adoption reject remote browser security_invite requests; only OS-local CLI/recovery may create distinctly marked local-recovery invitations. Local-only invitation recovery remains explicit and per-bridge, cannot sign/change the account roster or overwrite an account root. Remote browser per-bridge revoke of account members must explain account revocation instead of leaving a bypassing local grant. Track grant provenance.

Disallow last-account-admin revoke. Losing every nonextractable signing key still requires explicit reset/rebootstrap of each existing bridge (not implemented as an automatic reset). OS-local recovery can access one bridge but cannot restore account signing authority. UI gives clear instructions; never resets because database list is empty. Solo remains its independent bridge-only model.

## Errors, verification, and ownership

AccountTrustFailure is sanitized; account HTTP failures use AccountApiError with nested error {code,message,retryable}, and AccountErrorCode is included in existing bridge SecurityErrorCode. Existing generic HTTP auth failures retain standard401/403; consumers handle those statuses before parsing account errors. Invalid signature/context/enrollment: stop and start a new verified request; conflict: refetch/review/re-sign; rollback/key mismatch/revoked: close access, no automatic repin; offline expired: reconnect or local recovery; last admin: approve another device first; capacity/storage: display actionable error, no fallback. HTTP400 invalid,401 auth,403 cross-owner/permission,409 CAS/last-admin,410 expired,413 bounds,503 storage. Pure functions expose relevant typed codes; no secret-bearing raw exceptions.

Acceptance tests: first bridge single confirmation; second browser once across2bridges; third bridge automatically available; refresh persists keys/pins; migration removes browser-grant bypass; account revoke stops control/publication/queued responses after learned; last-admin rejected; cross-owner, swapped key/request/secret, replayed expired enrollment, stale/forked history and known-root empty reset denied; parallel CAS only one wins; offline grace does not slide on failed/invalid reads or clock rollback; MCP selected-only/no-admin/online-error; Solo/local recovery regressions; mobile rendered approval/device list/consent; existing full unit/type/build checks and focused E2E. Root executes all browser/E2E/DB/server work. No production migration/deploy/merge.

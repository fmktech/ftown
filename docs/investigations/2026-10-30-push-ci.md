# Concurrent duplicate push 503

## Symptom and artifact evidence
Run 41106415985, Node24.22.1 Linux, `e2e/tests/push-notifications.spec.ts:146`: parallel duplicate question requests expect both 202; one returned 503. 70 tests passed including the original failures. Trace's 503 response resource is exactly `{"error":"push_unavailable"}`, not `{accepted:true,pending:...}`. The CI Postgres log at `/tmp/ftown-pr167-ci-second-artifacts/ci-infra.log:119-126` records:
```
ERROR:  duplicate key value violates unique constraint "push_events_sub_bridge_id_session_id_event_key_key"
STATEMENT: WITH created AS (
  INSERT INTO push_events(id,sub,bridge_id,session_id,event_key,kind,payload,occurred_at)
  VALUES($1,$2,$3,$4,$5,$6,$7::jsonb,$8::timestamptz) ON CONFLICT(id) DO NOTHING RETURNING id,sub,occurred_at)
```
The route maps non-`PushError` exceptions to 503 `push_unavailable`. `eventIdentity` hashes `[owner, bridge, event.sessionId, event.eventKey]`; `0005_web_push.sql` also independently has `UNIQUE(sub,bridge_id,session_id,event_key)`. Both index uniqueness checks address the same logical identity, but target `ON CONFLICT(id)` designates only the primary-key arbiter. The exact cause of this particular SQL error is observed; concurrency behavior needs isolated reproduction before any product edit.

## Hypotheses

#### H1: Concurrent identical inserts bypass the primary-key arbiter yet collide on the independent tuple unique index.
- **Layer**: database concurrency
- **Prediction**: concurrent calls with equal logical identity and deterministic ID can cause `23505` naming `push_events_sub_bridge_id_session_id_event_key_key`, despite `ON CONFLICT(id) DO NOTHING`; no duplicate logical row exists. A targetless conflict handler should suppress both unique conflicts while preserving one event and snapshot.
- **Verification**: CI DB log plus isolated real-store/Postgres harness; targetless alternative requires separate approved counterfactual fixture, not product edit.
- **Evidence**: CI log quoted above. Root ran actual PushStore, exact migration and synchronized two-client 50-pair isolated DB harness: exit 1, 18 successful pairs, 32 matching natural-tuple 23505 errors, 0 other failures, 50 events, 0 deliveries; scratch schema cleaned. `eventIdentity` hashes the same tuple.
- **Verdict**: PROVEN.
- **Rationale**: The exact CI constraint failure occurs with independent clients and identical deterministic IDs in an isolated scratch schema.

#### H2: Delivery retries with a pending recipient cause 503 without an insert error.
- **Layer**: API/data
- **Prediction**: response body is `accepted:true,pending` with pending >0 rather than error; no insert constraint failure.
- **Verification**: inspect exact trace response and DB log.
- **Evidence**: body `{"error":"push_unavailable"}` and timestamp-matched Postgres 23505, not accepted/pending. The test removed its only subscription before the duplicate question.
- **Verdict**: REJECTED for this particular CI response.

#### H3: External transport or database connection instability produces the failure instead of unique constraint arbitration.
- **Layer**: infrastructure
- **Prediction**: errors show network/connection/timeout rather than a SQL statement/constraint violation.
- **Verification**: inspect Postgres and shim logs, trace response; attempt isolated local Postgres reproduction.
- **Evidence**: CI PostgreSQL log and root isolated 50-pair run both report the named natural-tuple unique violation; isolated run has zero other failures.
- **Verdict**: REJECTED for reproduced failure.
- **Rationale**: Database returns a specific integrity violation, not a transport or connection error.

## Root cause, five whys, and falsification
1. A duplicate POST receives 503 because the ingest INSERT raises a natural-tuple unique violation, mapped to generic `push_unavailable`.
2. The insert's `ON CONFLICT(id)` handles only the primary-key arbiter; concurrent identical speculative insertions may violate the separate natural-tuple index.
3. Event identity is deliberately enforced redundantly by both the deterministic hash ID and tuple unique constraint; conflict handling addressed only the former.
4. Existing duplicate coverage included concurrent E2E but did not isolate actual database interleavings and had passed prior runs.
5. The implementation lacked a real-database concurrency regression for both independently enforced unique indexes.

Isolation/falsification: the real PushStore with fixed identical input, no HTTP, no provider, and no subscriptions reproduced 32 matching violations in 50 pairs while creating exactly 50 event rows and no deliveries; this rejects H2's pending-delivery and H3's external transport alternatives for the failure. A targetless handler is a counterfactual to validate post-fix, with fail-closed legacy mismatch and snapshot/ownership checks to ensure it does not conceal incompatible data. The exact failure and mechanism are proven before product edits; no other CI failures are inferred.

## Approved repair
Root and R3 froze a narrow `ON CONFLICT DO NOTHING` for this INSERT, preserving deterministic ID lookup scoped to owner, created-only recipient snapshot and all other routes/security. Real DB regression must check concurrent duplicates, later-subscriber non-backfill, original generic payload, bridge/owner separation, legacy natural tuple with mismatched ID remains 503, and nonunique CHECK failures. Root alone executes DB/E2E. No migration or natural-key fallback.

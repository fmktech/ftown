# Pending device approval — frozen v1.4

Root owns this specification and `bridge/src/security/pending-approval-protocol.ts`. Frozen after three independent reviews and their bounded amendments. Existing account/E2EE contracts remain authoritative except the explicit additions below. Implementation workers must not invent or amend a seam; report gaps to root.

## Product and boundaries

A new logged-in browser automatically creates one approval request, keeps its identity, and shows Waiting. A trusted dashboard shows Pending approvals in Security → Devices, a count on Security, and a mobile-visible Review entry. Reviewing is not approval. Both actual devices display a verification code and require a positive local comparison confirmation. The trusted browser then signs membership; the candidate automatically connects. An untrusted browser cannot approve itself or another device. Incoming links opened there show its own waiting state with a clear explanation, retaining the intended continuation separately.

A virgin bridge can supply `--account <email>` (or an interactive account prompt) to appear in that account's inbox. Email is routing only. No account lookup or disclosure occurs at anonymous start; no anonymous-triggered push. Existing bridge reauthentication preserves its bound keys and root. Explicit first-account/private-link bootstrap and local recovery remain available and never activate as an automatic protocol downgrade. MCP keeps exact selected-bridge scopes and independent consent; its unapproved browser can wait and resume consent without losing the continuation.

The server relays public requests, commitments, ciphertexts, reveals, MACs and signed history. It never receives a plaintext bootstrap secret, signing private key, or candidate secret. An approved bridge cannot sign account device membership; the existing trusted browser handles approval. Existing endpoint/transport encryption and security audit behavior remain intact.

## Encryption and comparison protocol

This is a new FTown protocol using existing HPKE Auth (P-256/HKDF-SHA256/AES-256-GCM) and a committed hidden reviewer contribution; it is not Matrix-compatible or externally audited. Commitment prevents offline chosen-secret matching against a short code. Relevant design references: [RFC6189 §4.4.1.1](https://www.rfc-editor.org/rfc/rfc6189.html#section-4.4.1.1), [Jarecki–Saxena §4](https://nsaxena.engr.tamu.edu/wp-content/uploads/sites/238/2019/12/js-scn10.pdf), [RFC9180](https://www.rfc-editor.org/rfc/rfc9180.html), [RFC5869](https://www.rfc-editor.org/rfc/rfc5869.html). Their security results do not automatically prove this adaptation.

Canonical encoding is existing recursively sorted JSON, UTF-8, no undefined/nonfinite values, strict exact keys and bounded canonical unpadded base64url. Separate domain strings below end in newline. Every random contribution, nonce, offerId and request credential is 32 random bytes. No suite negotiation.

1. Candidate publishes existing public `AccountEnrollmentRequest`, no secret. Browser owner UUID comes from authenticated login; bridge starts with `pending:<bridgeId>` as before. Candidate persists request/credential before HTTP. Repost of exactly the same request/credential is idempotent.
2. Trusted user selects Review. Browser refreshes/validates its pinned history, checks itself active, freezes the exact request and pre-append head, and generates random reviewer contribution R and offerId. Offer core binds method/version/suite, exact request and keys, owner UUID, root/pre-head, approver HPKE/signing keys and expiry (equal to request expiry). Commitment is SHA256(`ftown-pending-commit-v1\n` + canonical `{core, contribution:R}`). Sign offer payload (including commitment) with ECDSA using `ftown-pending-offer-v1\n`. Persist offer+R BEFORE publishing it. Signature bytes never contribute to SAS entropy.
3. Candidate verifies offer syntax/self-signature and exact request/owner bindings. A self-signed offer alone is not trust. It durably pins one exact offer before generating fresh candidate secret S. Normalize pending bridge endpoint owner only inside this exact offered context. HPKE Auth-seal plaintext `{type:'ftown_pending_secret',version:1,requestId,offerHash,secret:S}` to offered approver. Envelope channel `pending-approval:<requestId>`, purpose `enroll`, bridgeId requested bridge ID or `account_<ownerId>`, messageId requestId, receiverEpoch null, expiry min(now+120s,request expiry). Persist the exact hello and nonextractable HKDF key imported from S before transmission. Never regenerate S or reseal a different hello under that request/offer after publication.
4. Approver durably pins exactly one hello digest BEFORE decrypting/revealing. Invalid ciphertext consumes the offer and rejects the request even if rejection HTTP fails; never accept replacement after reveal. Open authenticates the candidate's exact HPKE key and every context field, including unexpired first receipt. Atomically persist `PendingReviewerOpened` with nonextractable PendingSecret, offer/hello hashes and successful openedAt BEFORE revealing R. Reload/renewal uses that retained key; it does not reopen an expired hello. Loss of retained key requires an explicit fresh attempt. Reveal binds the offer hash. Candidate verifies the commitment before displaying any code.
5. `offerHash` = SHA256(`ftown-pending-offer-hash-v1\n` + canonical unsigned offer payload). `helloHash` = SHA256(`ftown-pending-hello-hash-v1\n` + canonical hello). Derive HKDF-SHA256 with IKM=S, salt=SHA256(`ftown-pending-salt-v1\n` + canonical `{offerHash,contribution:R}`), info UTF-8 `ftown-pending-v1/<label>`. Labels `sas` (6 bytes), `candidate-confirm` (32 bytes), `approver-result` (32 bytes), `bootstrap` (32 bytes) are distinct. SAS displays the six bytes as uppercase `XXXX-XXXX-XXXX`. Ciphertext randomness/signature bytes/post-offer values never alter SAS. Local private key is nonextractable HKDF; derived keys/material are short-lived and never logged/uploaded.
6. Positive local candidate confirmation stores the exact offerHash, then HMAC-SHA256 with candidate-confirm key over `ftown-pending-candidate-confirm-v1\n` + canonical `{role:'candidate',requestId,offerHash}`. A relay state saying confirmed cannot replace this local action. A local negative comparison cancels and requires a fresh explicit attempt; no automatic retry or approver replacement.
7. Positive local trusted confirmation also stores the exact offerHash. Only with that AND a verified candidate MAC can the trusted browser prepare the signed exact member addition at the offered pre-head. If the exact candidate/key/label is already active at that anchor, use no transition. Otherwise exactly one add_device/add_bridge transition is allowed, with same signer as offer. Changed pre-head before first finalization aborts with an explicit new verification; do not silently retarget.
8. Build the existing `AccountEnrollmentBundle` with a separately derived bootstrap secret, using the exact approved history prefix (anchor or anchor+one addition). Result includes this head and a MAC under approver-result key over `ftown-pending-result-v1\n` + canonical `{role:'approver',requestId,offerHash,head,bundleHash}`; bundleHash=SHA256(`ftown-pending-bundle-v1\n` + canonical bundle). No result may be created without local trusted confirmation and valid candidate MAC.
9. Candidate requires its durable local confirmed offerHash, valid reveal and result MAC, exact request/approver/owner/head bindings, and the offered root/pre-head prefix in independently fetched authenticated current history. Result head must equal anchor for exact existing membership or anchor+one exact signed addition. Open the existing HPKE/HMAC approval against that prefix, then verify current full continuation/candidate still active. Atomically persist verified trust before access; obsolete request cleanup afterward is best effort. Mere login, server status, self-consistent history or a displayed code never grants access.

Both confirmations are mandatory: without candidate confirmation a malicious relay can make an unpinned candidate trust a fabricated account. With commitment and locally pinned one-attempt transcripts, the code provides approximately 48-bit per-attempt comparison protection, not the prior 256-bit out-of-band secret assurance. Do not claim automatic protection if users ignore mismatches. Server may withhold/fork; no global consensus or instantaneous revocation guarantee.

## Persistence, concurrency and retries

Browser IDB owns a versioned per-owner/candidate request record and per-request reviewer record, using transactional CAS to select one request, one offer and one hello across tabs. Async crypto occurs after obtaining the corresponding lock and before atomically storing the result; no network publish precedes storage. Record local confirmation by exact offerHash. Lost candidate HKDF key/reviewer contribution requires explicit cancellation and fresh verification, preserving long-term identity. Reload with valid state resumes the exact transcript; never creates a second hidden attempt. Dispose/account-change guards discard old async completions. Sign-out stops polling and erases only task continuations according to existing owner isolation.

Bridge uses existing0600 atomic pending storage for candidate identity/request. Candidate S stays in running-process memory. Process loss of S requires cancellation/new request, never a new S under an existing offer. Two separate0600 snapshots provide local IPC: bridge alone writes `pending-approval-status.json`; CLI alone writes `pending-approval-confirmation.json`. AtomicSnapshot does not synchronize separate processes, so they must not update a shared document. Status/confirmation bind version, requestId, processNonce, offerHash, expiry and displayed code/decision; bridge validates against live memory before making a MAC. No keys, S or unrevealed R in public status. `ftown security pair-status` displays local phase/code; `ftown security pair-confirm <XXXX-XXXX-XXXX>` confirms the exact current comparison; `ftown security pair-reject` cancels. Existing global --data-dir selects local files. TTY may show code and ask yes/no; background logs only instructions to pair-status. Restart, expiry or cancellation makes old confirmation invalid. No local API pointer or new remote unauthenticated confirmation endpoint is required.

CLI startup: `--account <email>` explicitly selects pending-v1 for a virgin bridge. `--bootstrap` explicitly selects existing fragment bootstrap and conflicts with --account. Without either flag, interactive virgin startup asks for account email; an explicit blank answer selects first-computer fragment setup. Noninteractive no-flag startup retains existing fragment behavior and advertises --account, because no pending-v1 attempt has been chosen; once pending-v1 starts, no fallback is automatic. Explicit restart into bootstrap cancels the old attempt best effort and creates a different request while preserving candidate key. Existing bound reauthentication ignores no trust pin and never enters candidate key generation.

All network operations have15s deadline plus lifetime abort. Poll2s with one in-flight operation; successful validated transitions remove superseded transient errors. Terminal rejected/cancelled/expired/conflict stops polling. Network interruption keeps local state and permits retry. Unauthorized reviewer UI cannot show an enabled approve action; old authority errors disappear only when a newer validated state supersedes them. No optimistic success or automatic mutation replay with changed payload.

Server monotonic state: pending → offered → submitted → comparing → confirmed → approved. Rejection/cancellation may win before approved; expiry is terminal. Exact duplicate operations return their committed state before checking stale supplied revision. Same operation with conflicting payload fails409; it cannot replace offer/hello. Idempotency is keyed by request+actor+canonical signed/secret-authenticated payload, not only a random HTTP header.

First finalization atomically CASes signed history, pending result/state, and linked bridge pair approval. Validate prospective signed history and bundle before writes. Lock participants in one consistent order and gate every write on complete eligibility, with checked all-or-zero write counts. Cancellation and finalization race on the same pending revision. A lost response permits the exact final digest to be replayed without another roster addition. Do not implement separate append-then-publish for this new protocol.

Existing response envelopes live120s. Approved requests may renew delivery while their original5min request remains valid: trusted browser restores the exact persisted contribution and validated PendingReviewerOpened secret, verifies its local confirmation and candidate MAC, fetches fresh history (candidate and approver still active), and reseals against the IMMUTABLE approved history prefix. A separately signed renew command atomically updates delivery bundle and any unconsumed bridge pair bundle, not membership/head or request expiry. The candidate code/confirmation remains unchanged. `openPendingResult` returns typed `awaiting-delivery-renewal` only after validating result MAC/bindings/current history while request remains live; it never opens expired ciphertext. `parsePendingState` permits an approved state containing expired delivery. Invalid MAC/context and request expiry stay terminal. Automatic renewal while the trusted approval view is open is permitted; UI explains reopening trusted approval if delivery expired. After5min a fresh explicit request may approve the exact existing member without duplicate addition.

Bridge credential delivery is separate from approval finalization. Pending-v1 polling must atomically consume the approved pair row and persist its one refresh JTI. Repeat polling of the exact private deviceCode during the original request lifetime may return credentials for that same JTI ONLY if bridge_refresh still contains the exact owner/bridge/JTI. Never rotate/re-upsert on repeat, resurrect revoked credentials, or extend pair expiry. A rotated/revoked JTI fails closed. Token replies are minted from persisted claims; a lost first reply therefore resumes without a new enrollment. Legacy/auth-only flow remains unchanged unless required to reuse a safe shared helper.

Persist the first delivery's owner UUID/subject, bridge ID, JTI, each token's iat/exp and other required claims, connectedAt and validated advert in the pending record. Duplicates ignore changed advert and use the exact immutable snapshot; no timestamp/lifetime extension. After first credential reply, runPairing retains those credentials and polls candidate RPC for the latest approved result while awaiting renewal. It does not depend on or re-consume the pair row's cached bundle; that bundle may be the original expired delivery. Fresh configured-origin account GET and result verification remain required before installing trust.

## API/store and migration

Types/routes in pending-approval-protocol are authoritative. Browser create/inbox/read and reviewer commands require same-origin browser session, immutable owner isolation, no-store responses and existing bounded rate limits. Candidate RPC is POST with a random client-generated per-request candidateToken, SHA256 stored; it can read/send hello/confirm/cancel only its own request. It cannot add membership. Public request IDs and email hints are not credentials.

Pending-v1 bridge start, like browser create, includes a client-generated candidateToken persisted before HTTP. Candidate RPC uses that token; the existing pair poll uses a separate server-generated deviceCode. Exact start retry (request+candidateToken+hint) returns the SAME pair row/deviceCode, including after a lost start reply. Only the new candidateToken is stored hashed; existing private deviceCode storage is unchanged and never exposed in inbox/owner review. `runPairing` owns the entire pending ceremony and retains S, then uses returned temporary credentials to fetch fresh history from the configured API origin, calls openPendingResult, and returns local-only PendingPairingVerified with verifiedAccountTrust/lastServerReadAt. Index binds the same pending key using this verified result; it never routes pending-v1 through fragment openAccountApproval or treats server-supplied history as a fresh read. Pending API requests reject redirects and nonconfigured origins; deadline includes bounded whole-body parsing. maxWireBytes64KiB covers commands/state/pair replies, maxInboxBytes512KiB covers128 summaries, and existing account history limit2MiB remains separate.

Reviewer mutation commands are ECDSA signed over `ftown-pending-action-v1\n` + canonical payload, including exact action/request/revision/current account head/actor/issuedAt. Verify current active signer and exact request/target owner, signature, expiry and30s skew. Review embeds the signed offer. Reveal binds helloHash and commitment. Finish binds transition/result; null transition permitted only exact existing active member. Renew keeps original final semantics. Reject also requires trusted signer. Browser cookie alone cannot approve/reject another candidate. Invalid untrusted input uses sanitized existing account error shapes/statuses; public parsers have unknown only at JSON boundaries.

Anonymous pair/start accepts explicit `approvalMethod:'pending-v1'` and normalized `accountHint` plus enrollment. Store hint directly as routing, without looking up whether an account exists. Same response shape for existing/unknown email. No account name/history/queue status is disclosed anonymously. Current account emails are not normalized at registration: authenticated inbox/review must check normalized routing matches exactly one immutable user UUID; ambiguous addresses fail closed with an authenticated actionable conflict, never select an arbitrary account. No auth normalization migration is included. Source/target/global quotas and5min expiry bound abuse; no anonymous push. Pending list returns public summaries only, max128 per owner (UI may display32 and Show more). Global live queue max4096, wire body64KiB, expired cleanup bounded1000. Never include candidate credential, fragment secret, R before reveal, or S in inbox/logs/notifications.

New additive0008 migration introduces a unified pending approval table containing exact request, target_sub, optional owner UUID/linked pair device-code hash, credential hash, state/revision, immutable final digest/head, delivery state, expiry and target slot. Old tables/migrations/rows unchanged except nullable pair linkage if unavoidable. New indexes on new empty table. Bounded lock_timeout/statement_timeout; no backfill/destructive step. Deploy schema before app. Rollback app leaves public pending records to expire; do not drop established account history. Root alone executes migration on a verified isolated database. Real database checks must cover owner isolation, duplicate create/review/final, cancel-vs-final, stale head, target/global caps, expiry, old rows unchanged and repeat migration.

Capacity is enforced by unique constrained target slots0..127 and unique global_slot0..4095, not COUNT+INSERT. Expired rows release slots only through bounded cleanup; concurrent collision retries remain bounded. Normalization in JS and SQL is exactly trim ASCII U+0009–000D/U+0020 at either end and fold ASCII A–Z to a–z, preserving all non-ASCII characters byte-for-byte; validate <=254characters, one @ with nonempty sides and no remaining control/whitespace characters. SQL uses btrim with that explicit character set then translate with ASCII alphabet (no locale-dependent lower). Authenticated lookup reads at most2 matches and requires exactly1 equal to session UUID; repeat uniqueness/target eligibility inside mutation SQL. Anonymous start never performs this lookup.

Server validation seam: extract `validateApprovalAgainst(ownerId,request,bundle,verifiedHistory,options)` from existing AccountTrustStore validator; keep current-history-reading wrapper for legacy callers. Finalization validates prospective history before writes; renewal validates immutable approved prefix plus current active candidate/reviewer. Final SQL locks pending→history→pair, recognizes exact finalized digest duplicate before stale-head checks, gates every write on full eligibility, and uses RETURNING dependencies. Its top-level result must evaluate a checked all-or-zero count assertion (e.g. integer division by CASE yielding zero on impossible partial writes) so an unexpected downstream zero aborts the entire statement. No separate app-side mutations with a partial-success response.

Core uses existing AccountTrustFailure: malformed/signature/context/MAC→account_enrollment_invalid (stop/new explicit attempt); expired→account_enrollment_expired (stop); stale/competing→account_trust_conflict (review new attempt); unapproved/revoked→existing respective errors (no access); capacity/storage→existing codes (retry only same retained request where safe). Terminal state explains rejected/cancelled separately. HTTP400/401/403/409/410/413/429/503 follow existing conventions; never raw DB/crypto errors. No new dependencies or production secrets.

## Amendment v1.4 — atomic browser completion and cancellation

Independently reviewed by account_server_review. No wire/crypto contract changes. Completion must check the exact locally verified owner, candidate, request, offer, confirmed offer hash, active phase and revision alongside the existing trust CAS in one IndexedDB readwrite transaction spanning account-trust and pending-candidates. Only that transaction may persist trust and retire/complete its candidate record. Crypto and fresh-history verification happen before this transaction; guards remain bound to that verified transcript and never retarget to a newer record. A losing completion discards stale work and reloads local state without exposing ready. Cancellation uses CAS/reload and preserves an already committed approval instead of falsely reporting cancellation. A cancellation which commits first prevents later trust installation, including sibling-tab races. Regressions must hold the history/result await, cancel locally, then release the valid response and assert no durable trust; independently cover the native storage transaction and already-completed outcome.

The local comparison click is also bound to the exact request, offer and code actually rendered by that UI event. Capture that tuple before any await; asynchronous refresh, sibling-tab restart or changed selection must never retarget the click. Subsequent candidate/reviewer durable reads and CAS must match the captured tuple. A mismatch refreshes state and requires another explicit comparison click. Both candidate and reviewer controls use the same rule.

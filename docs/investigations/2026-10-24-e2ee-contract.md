# FTown encrypted endpoint protocol

FROZEN CONTRACT — immutable once fan-out has started. If this contract is wrong or incomplete, STOP and report to the architect; do not amend locally. Types are in `bridge/src/security/protocol.ts`. Repository changes remain on one shared checkout. Root implements no application bodies. Three independent scope reviews were completed; accepted corrections are incorporated below. A short final interface consistency check precedes dispatch.

## Security boundary and product decisions

1. Every browser/PWA installation, bridge and MCP OAuth grant is a distinct cryptographic endpoint. Hosted MCP is trusted with plaintext tool calls/results; ordinary MCP clients use HTTPS/OAuth to it. Its bridge-facing private key is stored only as authenticated ciphertext in PostgreSQL. No model PIN or extra helper.
2. Use RFC9180 HPKE Auth, DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM via maintained `@hpke/core`; no custom ECDH cipher. One fresh encapsulation per recipient/message. This release makes no forward-secrecy or post-quantum claim. The same neutral crypto implementation is consumed by Node and browser.
3. Cloud is an untrusted content relay and public-key discovery service. Public directory rows alone never authorize a sender or replace a pinned bridge key. Each bridge keeps a durable locally approved client-key list with read/control/admin permissions; browser/MCP endpoints pin each bridge key.
4. Initial trust uses an explicit bridge-generated invitation: random 32-byte one-use secret, five-minute lifetime, exact account/bridge/public-key binding. The bridge displays an HTTPS `/connect` invitation with secret and pinned key ONLY in the URL fragment. This dedicated page captures/scrubs the fragment before analytics or auth navigation, holds it in memory through inline login, compares authenticated immutable account, and submits the secret only inside an HPKE-authenticated enrollment packet to the pinned bridge. Never persist it or copy it into query/callback URLs, server actions or telemetry. Lost/expired invitations require a new one. No request-body/URL/secret logging. Login remains necessary for cloud routing. A trusted browser admin can request fresh invitations for additional devices; bridge-local CLI can always recover by issuing a new invitation. Invitations grant browser admin only after explicit confirmation showing bridge/account; MCP approvals never get admin.
5. The browser generates/persists a non-extractable private CryptoKey in IndexedDB, namespaced to the immutable logged-in account. No private key in local/sessionStorage or server responses. IndexedDB availability and a secure context are required; unsupported/insecure LAN HTTP gets actionable HTTPS/localhost guidance, never plaintext fallback. This is browser storage, not a promise of Secure Enclave/hardware protection. Losing storage requires fresh approval.
6. Bridge key and trust policy persist under instance dataDir with restrictive permissions and atomic writes. MCP private-key envelopes use a separately provisioned random 32-byte wrapping key, `FTOWN_MCP_KEY_ENCRYPTION_SECRET`, mandatory key ID, AES-256-GCM random nonce, and AAD binding version/account/grant/endpoint ID. The wrapping key is never in DB, runtime archives, source or logs. Missing/wrong key fails closed; deployment preserves existing secret and requires explicit provisioning for first rollout. No key regenerated silently on decryption failure.
7. Revocation removes the endpoint from each bridge's locally approved policy, immediately closes direct peers, clears cached authorization and prevents future encryptions/commands. UI shows pending/offline bridges honestly. Directory deletion is a denial signal, not sufficient enrollment authority. Lost private keys cannot be recovered by password reset.

## Wire contract

`EndpointPublic`: `{ version:1, id:string, ownerId:string, kind:'bridge'|'browser'|'mcp'|'local-cli', publicKey:string }`; publicKey is canonical base64url uncompressed P-256 public bytes; id is SHA-256 fingerprint of those bytes. Labels are display-only and bounded. ownerId is the immutable authenticated user UUID, distinct from the existing email used in Centrifugo channel routing; bridge auth/refresh metadata must carry this ownerId. Solo uses `solo:<bridgeId>` as an explicit local owner namespace. Keypair APIs always pass full CryptoKeyPair, including public key, so private keys need not be extractable.

`SecureEnvelope`: `{ type:'ftown_encrypted', version:1, senderId, recipientId, ownerId, bridgeId, channel, purpose:EnvelopePurpose, messageId, createdAt:number, expiresAt:number, receiverEpoch:string|null, enc:string, ciphertext:string }`. The authoritative purpose union in protocol.ts includes application/hello/welcome/enroll/enrolled/mcp-approval. Numeric times are milliseconds; enc/ciphertext are canonical base64url. The complete ordered header tuple (all fields except enc/ciphertext) is AAD with a fixed `ftown/e2ee/v1` domain separator. The recipient public key and pinned sender public key are required for HPKE Auth. Unknown fields/versions, invalid keys, excessive lengths, mismatched owner/bridge/channel/recipient and failed tags are rejected. No raw exception or ciphertext in log messages.

`SecurePublication`: `{ type:'ftown_encrypted_batch', version:1, envelopes:SecureEnvelope[] }` allows bridge broadcast independently sealed for each approved recipient. No unencrypted payload fields. Bound recipient count and total size. Stream chunking occurs before encryption; never truncate ciphertext. Serialize asynchronous seal/open work per channel to preserve terminal/event ordering.

Application plaintext is the existing JSON message, preserving existing session/RPC/event contracts. Internal trusted same-process/loopback calls after endpoint decryption are not a new remote endpoint; outward client transports must use the secure envelope.

Client→bridge executable envelopes require the current random receiver boot epoch, bounded expiry (maximum two minutes, 30s future skew) and a non-reused messageId. A read-only authenticated `hello {challenge}` obtains encrypted `welcome {challenge,receiverEpoch}` from an already pinned bridge; client accepts only its unpredictable pending challenge once, with matching account/bridge/key/channel. Hello may omit epoch and cannot invoke application handlers. The bridge claims each executable messageId before executing, serially, and never executes a replay. A fresh boot epoch invalidates captured pre-restart commands. Resource bounds fail closed rather than evicting live replay IDs. Historical bridge→client publication recovery may display older authenticated events; it can never drive commands. Tamper/replay tests cover every transport.

Opening an application envelope returns a VerifiedPrincipal (approved endpoint, permission, optional MCP grant) plus bound context, never just JSON. Preserve this through every command/terminal/local handler. Require `read` for session/history/list/watch, `control` for terminal input/resize/create/update/kill/mail/attention mutations and `admin` for approve/revoke/invite/security-policy operations. Owner alone is insufficient. Deny unknown commands/routes/frames by default; exact existing operation mapping is implemented/tested centrally by bridge owner. MCP runtime additionally enforces its OAuth scopes and selected bridge set. Target session/request/action IDs must agree with authenticated payload and selected bridge; bridge ownership checks remain. Channel/purpose uses distinct canonical namespaces for cloud channels, local RPC, local events and direct terminal frames. Direct peers bind an approved endpoint at encrypted handshake and check authorization on every input/attach/resize; revocation closes by endpoint ID, not claimed tab ID.

`enroll` is the only pre-authorization purpose. It carries the candidate public endpoint, invitation secret and requested display label inside ciphertext. An explicit `{type:'ftown_enrollment',version:1,candidate:EndpointPublic,envelope:SecureEnvelope}` wrapper carries the candidate public key solely for HPKE Auth; it conveys no authorization. Candidate/envelope/inner endpoint fingerprints, owner and kind must agree. The bridge verifies one-use secret/key/account/bridge/expiry binding and atomically consumes the invitation and persists approved policy in one serialized durable update before encrypted acknowledgement. Permissions come exclusively from the stored invitation, never requested fields. Existing cloud-visible `localNonce` must never enroll an encryption identity.

Canonical endpoint IDs are base64url SHA-256 public-key fingerprints (43 characters). Binary values use unpadded canonical base64url. Public P-256 keys are uncompressed 65-byte points. Native subtle.generateKey with extractable=false creates browser pairs; do not use a library helper that silently makes private keys extractable. The selected library has published test-vector coverage and is not represented as formally audited. Browser identity initialization uses IndexedDB add-and-reload-winner semantics so concurrent tabs never overwrite keys or pins.

Use a request-bound Fleet context carrying endpoint/keypair, immutable pinned bridges/permissions, owner, grant and action metadata; never a global mutable current identity. Keep shared concurrency bounds separate from per-request authorization. MCP bridge pins and granted permission metadata live inside the authenticated at-rest identity record, not unsigned directory records. Consent is bounded to 64 bridges and a 512KiB body; reject over-limit inputs explicitly.

## Lifecycle and surfaces

- Bridge presence/auth/channel identifiers may remain visible metadata, including account/bridge/session IDs, hostname, online status, sizes/timing, protocol/key IDs. Remove cloud-visible local authorization capabilities. Session names, paths, commands, terminal contents, mail, prompts/results, PR data, attention messages and SDP/ICE content are encrypted.
- Wrap cloud publish and all subscriptions before application handlers; preserve presence and transport lifecycle separately. Encrypt session snapshots, command/response, terminal input/output/screen, watch/unwatch, hooks/events/attention, and WebRTC signaling.
- Direct WebRTC and local HTTP/WebSocket use the same authenticated endpoint framing (DTLS/TLS can additionally protect transport). Direct fallback selects another encrypted route, never plaintext. CLI local API calls use a locally provisioned endpoint identity; exposed legacy HTTP/SSH MCP adapters must negotiate secure framing or reject with upgrade-required. Remove legacy native bridge_exec fallback. Raw bearer-authenticated local application routes cannot remain a bypass: native relay uses an internal non-exported capability/dispatcher with preserved verified principal; local agent hooks have a separate hook-only credential, which cannot call arbitrary application routes. Minimal health/discovery and hook ingestion are the only deliberate unencrypted local exceptions and appear in the documented endpoint boundary. Recheck current policy immediately before queued execution and egress, not only at decrypt time. Read permission is a semantic allowlist: for example an inbox read that consumes messages must be forced to peek or require control.
- Solo requires HTTPS or trustworthy localhost for browser crypto. Existing local pairing can be extended to deliver the same invitation, but cloud nonce auto-enrollment is removed. Health/auth/bootstrap discovery may remain minimal plaintext metadata; no plaintext command endpoint exposed to remote clients.
- New clients ignore/reject plaintext application traffic and show explicit pairing/upgrade state. New bridges never execute plaintext cloud commands. Existing bridge upgrades require enrollment; no silent compatibility switch. Plaintext chunks are bounded before sealing; split recipients into independent envelopes/batches to stay below the broker limit, with conservative wire maximum 450,000 bytes. Never truncate ciphertext. Broadcast only to currently approved recipients; revocation affects queued sends as well as connected peers.
- Push becomes content-free: generic FTown attention notice and opaque event/session routing references only; no session name, prompt/attention text, or PR detail. Opening the app retrieves details over the encrypted connection.

## Device and MCP approval UX

Dashboard has a visible Security entry with Devices and Activity views. Browser identity is initialized before transport hooks publish data. Unpaired bridges remain visible as metadata with a Pair action/instructions; session contents stay unavailable. Invitation review names the account and pinned bridge fingerprint. Ready bridges unlock automatically using locally stored non-extractable browser keys. Changed keys are an explicit re-pair state.

Invitation URL encoding is `/connect#invite=<encodeURIComponent(JSON.stringify(BridgeInvitation))>`; decode the URLSearchParams value once, then validate. Only an explicit local CLI invocation or an authenticated admin UI action displays the invitation. Background bridge startup logs instructions for obtaining an invitation, never the secret URL.

Recipient selection is deterministic: decrypted snapshots establish session→bridge mapping; list_sessions fans out only to ready pinned bridges; a targeted mutation without an authoritative target fails, never broadcasts. A newly paired bridge triggers its snapshot without disconnecting others. Local port is discovery metadata only: replace localNonce capability dependence with authenticated secure handshake. UI readiness is automatic local key availability, not a password unlock/security guarantee against same-origin code.

MCP OAuth consent obtains the exact public endpoint generated from its encrypted private-key record and the immutable grant identifier through the existing signed gateway consent channel. Reserve that grant ID and identity on the first subject-bound consent-details request, bind pending consent to that user, and preserve it through code exchange; never generate a different key or grant at exchange. The consent page runs browser-side encrypted approvals to the selected paired bridges, with read/control matching OAuth scope and no admin. Each bridge returns an HPKE-authenticated encrypted approval receipt for the MCP endpoint binding owner/grant/MCP key/bridge key/permission/expiry; browser forwards receipt and its pinned bridge public key. Gateway verifies/decrypts each receipt with its stored key and exact consent before persisting pins and finishing consent. A browser boolean is not proof of approval. Consent must not succeed with a silent unencrypted/unapproved fallback; offline approval is visibly pending/blocked. Existing MCP grants require renewed consent. Standard clients do not need to know private keys.

Devices list can inspect/revoke an approved endpoint on a bridge and create an invitation for another browser. Preserve own-device/recovery explanation. A new bridge can always be paired through its local CLI-generated invitation. No implicit trust based on display names/clientInfo.

MCP bridge approvals remain pending for at most five minutes and cannot execute ordinary application operations. Authenticated hello/welcome is permitted to the exact unexpired locally pending MCP endpoint to obtain a current boot epoch. After OAuth code exchange, the first request with a valid gateway-verified access token activates its own exact pending grant via encrypted `security_activate_mcp`; this is the only application command permitted to a pending MCP endpoint. Activation never extends the originally approved `activeExpiresAt` (maximum 30 days), reserved once by gateway consent details and included in McpConsentSecurity, approvals and receipts. Abandoned/cancelled/expired consent leaves only expiring pending entries, not permanent control. Reauthorization is explicit after active expiry. Idempotent activation retries preserve the original expiry.

## Endpoint/API seams

- Neutral Node/browser crypto implementation: `bridge/src/security/crypto.ts`; shared type contract above. UI aliases import it and resolve @hpke/core through UI-installed dependencies. No Node imports/globals in neutral core.
- `GET /api/security/endpoints` returns EndpointDirectory for session-derived owner. `PUT /api/security/endpoints` registers display-only public metadata for current browser, or verified bridge JWT with exact bridgeId/owner. It cannot authorize or revoke a bridge key.
- `GET /api/security/activity?bridgeId=&cursor=&limit=` is authenticated owner-scoped gateway SecurityPage. Errors are sanitized; API denies cross-owner filters/cursors.
- Signed MCP consent details add `security:McpConsentSecurity`; client-side consent completion sends requestId, selected bridge IDs and McpBridgeApproval[] to a session-authorized completion route. Gateway verifies exact receipts, grant/subject/scope, pins and expiry before approval. UI and gateway use the same frozen shapes.
- Local bridge `GET /api/security/info` returns only endpoint, ownerId, bridgeId and protocol version (untrusted discovery until pinned). `POST /api/security/envelope` accepts SecureEnvelope or EnrollmentPacket and returns SecureEnvelope; canonical channel `local-http:<bridgeId>`. HTTP route/method/request ID are encrypted in SecureApplication and must match dispatch. Raw local bearer application calls reject with upgrade_required. Local CLI recovery/invitation requires OS-local authority, never a cloud-visible bearer.
- Local events use `POST /api/security/events`, an authenticated encrypted long-poll with channel `local-events:<bridgeId>`. Application route is http GET to `/api/browser/events?after=<cursor>` (bounded integer cursor); result is LocalEventPage inside encrypted response, never raw events. Direct channels are `direct:webrtc:<bridgeId>:<pairId>` and `direct:loopback-ws:<bridgeId>:<pairId>`; pairId is the existing negotiated random direct-pair identifier, bound at encrypted hello and checked on every frame. Cloud channels remain their actual canonical Centrifugo names (for example `commands:rpc#email`), with no `cloud:` prefix. The direct first frame is a SecureEnvelope with purpose hello; the bridge returns encrypted welcome. Subsequent frames are encrypted SecureApplication values carrying existing DirectMessage data. There is no raw application hello. Loopback pairId is discovery metadata in `/ws?pairId=...`; WebRTC pairId comes from encrypted negotiated signaling. Expected channel is always derived from endpoint/transport routing, not copied from the incoming header.
- Hosted Dashboard passes immutable session.user.id separately from email routing subject. Solo/local clients must obtain BridgeSecurityInfo from `/api/security/info` and compare to invitation/persisted pins before application bootstrap. Plain discovery can never establish trust. BridgeSecurityInfo includes relayUserId only for existing routing.
- Security admin commands and result types are the `SecurityCommand` / `SecurityCommandResults` discriminated map. Flat command types map to existing wire framing `{type,requestId,payload:{bridgeId,...remainingFields}}`. Devices/invite/revoke/approve require admin; activity requires admin; activate requires the pending/active MCP endpoint matching its immutable grant only. BridgeSecurity implementation/export path is `bridge/src/security/bridge/security.ts`; interface is in protocol.ts.

## MCP activity log

Gateway audit is authoritative for authenticated attempts, including unknown/invalid tool calls, read/mutation, denied scopes, batches and calls that never reach a bridge. Bridge audit independently records received authenticated MCP operations and their execution outcome. Do not pretend a gateway timeout proves non-execution. Before execution, persist admission; if required audit storage fails, reject before mutation. Mark unfinished records interrupted/unknown on restart. Dedupe transport retries; preserve actionId correlation and individual batch child IDs. Bridge trusts audit context only from approved MCP endpoints and derives owner/endpoint/operation/mutation from verified principal and actual route. Record authorization rejections after authenticated identity verification. Once dispatch begins, uncertain storage/network failure must return outcome-unknown, never a safe-to-retry rejection; persist final outcome before response where possible.

`SecurityEvent`: `{version:1,id,actionId,parentActionId:null|string,ownerId,source:'gateway'|'bridge',bridgeId:null|string,clientId:null|string,grantId:null|string,endpointId:null|string,tool:string,operation:null|string,sessionId:null|string,startedAt,finishedAt:null|string,status:'started'|'succeeded'|'rejected'|'failed'|'unknown',errorCode:null|string,mutating:boolean}`. ISO timestamps. Tool/operation bounded validated tokens; safe failure code allowlist. Never persist raw args/results, headers, bearer tokens, private keys, paths, commands, query strings, prompt/search/mail text or arbitrary error messages. Unauthenticated requests with no trusted owner are server operational events, never attributed to a guessed user's history.

Gateway stores owner-scoped append/update events in Postgres. Bridge stores its independent events atomically under instance dataDir. Retain 30 days and at most 10,000 events per owner/bridge store, make boundaries explicit. Stable newest-first cursor pagination (default 50/max100), optional bridge filter, explicit truncation/reset handling. UI owner authorization derives from session, never caller query userId; MCP tokens cannot read this UI log by default. UI can show gateway history while bridge is offline and fetch bridge evidence through encrypted read RPC when connected. Label source/outcome uncertainty.

Gateway admission records include internal process run/lease ownership; reconcile only expired ownership, never mark another live replica's started operation unknown on startup. Sanitize unknown/invalid submitted tool names to fixed tokens; arbitrary attacker input is not log metadata.

Responsive Security dialog: persistent sidebar entry also in collapsed desktop state, per-bridge 44px shortcut, All bridges default; cards on mobile, time/action/target/client/status, source badges, refresh/load older and retention text. Empty/error/unavailable/upgrade states are explicit; preserve previous results on refresh failure; cancel stale filter requests. No raw HTML rendering or raw error disclosure. Opening/closing must not navigate/dismiss attention.

## Migration plan

Classification: additive new public endpoint discovery, encrypted MCP identity and security-event tables only. Existing OAuth/user/bridge records remain untouched; no backfill or destructive contract step. Old code tolerates added tables. New code must detect missing schema and fail with setup-required, never use plaintext fallback. Apply schema before rolling out gateway/UI; upgraded bridges pair with upgraded clients.

DDL: CREATE TABLE and indexes on newly empty tables; no rewrite/scan of hot existing tables. Foreign-key choices must avoid blocking current hot writes; owner scoping uses explicit validated subject. Apply with bounded lock/statement timeouts. Expected verification: tables exist, pre-existing user/OAuth row counts and hashes unchanged, encrypted key records never contain private JWK/raw secret, owner cross-read queries return zero records.

Rollback: retain additive tables (forward-only schema retention; no deletion of keys/audit). Roll back application only with bridge/device encryption still fail-closed; loss of encrypted connectivity is explicit, never downgrade. Fix forward and retain the wrapping key; do not regenerate it. Tests exercise apply/idempotency on populated isolated fixtures and prior code tolerance, not production.

## Native adapter local IPC clarification

Node/shell native adapters use the OS-local encrypted CLI client for business API calls. An internal `ftown security proxy` accepts one bounded stdin JSON value containing method/path/body/timeoutMs and returns a bounded `{status,body}` JSON result on stdout. No private keys, tokens, invitation secrets or content bodies in argv; subprocess calls use an argument array without shell interpolation. It uses the locally provisioned CLI identity, preserves HTTP status/error semantics, and does not grant authority to the hook credential. Existing `/hook` lifecycle ingestion remains within the documented trusted bridge/agent endpoint. Unsupported adapter runtimes must be verified against their actual API before selecting a proxy mechanism; do not invent executable APIs or silently restore plaintext business routes.

Encrypted HTTP `data` is `{body?, timeoutMs?, callerSessionId?}`. The optional callerSessionId is accepted only from a verified local-cli endpoint, as bounded 1–200 character ASCII `[A-Za-z0-9_-]` attribution metadata; it never grants authorization. The internal dispatcher may restore the existing x-ftown-session-id header for local session-parent/harness attribution. Browser/MCP callers cannot set this field; arbitrary headers are not forwarded.

The Claude mod runtime has no evidenced subprocess or WebCrypto API. Its existing trusted loopback hook IPC may use a fixed FtownNativeWake event with adapter claude-mod, exact stored FTown/native-session match and optional boolean registerWake to maintain the existing lease behavior. Response contains only unread opaque mail IDs. It cannot consume mail, return message content, invoke arbitrary routes or submit prompts. Intercept this internal event without publishing a normal lifecycle event. Existing hook-only authentication, loopback/origin guards and identity-conflict behavior remain. This is within the documented bridge/local-provider trust boundary, not a remote client encryption exception.

Request-bearing command/http envelopes use messageId equal to route.requestId. Terminal/publication frames receive fresh independent message IDs. Secure browser adapter injects authoritative selected bridgeId into each encrypted command payload and normalizes existing cloud terminal type frames into `{kind,sessionId,...}` inside ciphertext; public domain callers keep their existing API.

## Reviewed self-revocation acknowledgment clarification

An authenticated admin may revoke its own exact endpoint. The bridge may prepare one fixed encrypted response for that already verified security_revoke command before removal: only the existing correlated requestId and `{endpointId: senderId, revoked: true}` result in normal response framing. Release this presealed response only after durable policy removal and required audit completion. No generic post-revocation encryption capability, arbitrary result, publication, or subsequent content delivery is allowed. Revalidate before dispatch; failed commit/audit must never release success. Normal replay protection and immediate direct-peer closure remain. Lost acknowledgment is an uncertain result, never justification to restore approval or automatically replay a mutation. This narrow non-content receipt exception was independently reviewed by MCP worker before bridge implementation.

Invitation relayUrl is the configured/authenticated broker WebSocket URL (wss, or ws only for trustedloopback), never the web/API origin. CLI /connect links use the separate pointer.apiUrl. Browser cloud credentials continue to go only to authenticated same-origin bootstrap routing, never to this untrustedhint.


### Proxy-aware cookie mutation origin guard (2026-10-24 live repair)
A shared server-only predicate validates the exact Origin header against the request URL origin (existing direct-access behavior) or the separately operator-configured FTOWN_PUBLIC_URL origin. It never derives trust from Host/X-Forwarded-* headers. Missing/null/malformed origins are denied. Configured public URL must be HTTPS or trustworthy loopback HTTP, contain no credentials/query/fragment/nonroot path, and malformed configured values fail closed. Authentication and immutable owner checks remain separate and mandatory. The accepted origins are finite exact origins, never suffixes/wildcards. This preserves intentional direct localhost access while supporting TLS termination where Next constructs its Request URL with the internal listener port. Apply consistently to newly added cookie mutation endpoints and the existing push mutation wrapper. Required checks: proxy public origin accepted; direct request origin accepted; unrelated/forwarded-header-spoofed/missing/null origins rejected; invalid configuration and insecure nonloopback config rejected. Root independently reproduced public8444=>403 forbidden_origin vs internalHTTPS3000=>401 unauthorized before this repair.

# Dependency security updates

All changes use npm lockfile v3. Versions below are locked versions, not just manifest ranges. Node 24.22.1; final locks regenerated with npm 12.2.1 `--package-lock-only --ignore-scripts` after npm 11.6.2 removed unrelated cross-platform lock metadata. The final lock diffs contain only the named version changes, body-parser's declared dependency floors, and the required bridge package version bump. No data migration is introduced; rollback of a given change requires reverting its manifest, lock and associated code together. The package vulnerability returns on rollback.

## body-parser 2.3.0 → 2.4.0 (bridge)

[2.4.0 release](https://github.com/expressjs/body-parser/releases/tag/v2.4.0), [advisory](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828). The release fixes a late decompressor error, adds zstd support, avoids mutating read options, and updates qs/content-type/iconv-lite minimums. Express JSON middleware uses default inflation in `src/mcp/http.ts`; normal JSON and gzip behavior and post-response survival must be exercised by root's live regression. The new zstd support is an additive accepted encoding, not a disabled validation check; no application setting directly opts into it. No other installed package version changes except the separately tracked qs update; existing locked content-type/iconv-lite already satisfy the new floors. Body-parser 2.4.0 requires qs >=6.16.1, so these two changes are coupled for an atomic lockfile commit. Restore both lock resolutions together to roll back.

## qs 6.16.0 → 6.16.1 (bridge)

[6.16.1 changelog](https://raw.githubusercontent.com/ljharb/qs/v6.16.1/CHANGELOG.md), [advisory](https://github.com/ljharb/qs/security/advisories/GHSA-6pq8-jhm2-2vcw). Fixes comma-array stringify coercion, several stringify encoding edge cases and parse/merge bracket, dot, conflict and array-limit behavior. The application has no direct `qs.stringify`/`arrayFormat` use; Express/body-parser can use qs parsing, so changed handling of malformed/ambiguous query or form inputs is a dependency behavior change, not verified as byte-identical. Node `URLSearchParams` is used by bridge's own query encoder. The exact 6.16.1 override avoids silently jumping to a newer minor. No transitive packages moved. Rollback together with body-parser as above.

## fast-uri 3.1.8 → 3.1.9 (bridge)

[3.1.9 release](https://github.com/fastify/fast-uri/releases/tag/v3.1.9) fixes percent-encoded schemes, ambiguous hosts, relative reference normalization and suffix-reference scheme injection. It rejects or canonicalizes affected malformed references differently. Bridge does not directly import fast-uri or configure its `reference: suffix`; Ajv uses it transitively. Security-sensitive gateway origin checks use the platform URL parser. No transitive version changes. Revert its lock entry to roll back.

## undici 7.29.1 → 7.30.1 (UI dev only)

[7.30.0](https://github.com/nodejs/undici/releases/tag/v7.30.0) includes decompression backpressure, WebSocket lifecycle and diagnostics fixes; [7.30.1](https://github.com/nodejs/undici/releases/tag/v7.30.1) fixes TLS, redirect/cache, encoding and related security cases. It is an override of jsdom's dev-only dependency; no direct source imports or production path were identified. Node's built-in fetch is separate. No transitive versions moved. Restore override and lock to roll back. UI unit tests are owned by the UI worker/root.

## zod 3.25.76 → 4.6.7 (bridge and UI together)

[Migration guide](https://zod.dev/v4/changelog), [4.6.7 release](https://github.com/colinhacks/zod/releases/tag/v4.6.7), [early rejection fix](https://github.com/colinhacks/zod/pull/6652). SDK 1.32.1 supports both major versions. The v4 migration guide and upstream stable release history were inventoried; see the release review below for the two newly discovered compatibility changes, version coverage, and concrete upstream gaps. No transitive version changes. Roll back both packages and all associated source/test adaptations together; the prior collection-size vulnerability returns.

- `AnyZodObject` → `ZodObject`; snapshot generic uses `ZodType<T>` with `NoInfer<T>` so nullable snapshots infer from their schema. One-argument `record(value)` → `record(string(), value)` retains arbitrary string keys and partial entries.
- v4 UUID narrows acceptance; `string().guid()` restores v3's hex-and-hyphen grammar. Compared the installed v3 regex with v4 GUID regex and exercised non-RFC variant, nil, malformed and wrapped examples. UUID sites include persisted policy, account state, audit, MCP keys/events and attention cursors.
- v4 makes absent `unknown()` object fields invalid. Explicit `.optional()` restores v3 acceptance in enrollment/application envelopes, client responses, and MCP approval receipts; downstream validation and authorization remain in place.
- **Approved semantic change:** v4 `number().int()` rejects values outside the safe-integer range, which v3 accepted. Unsafe counters and persisted state fail closed instead of silently rounding. Valid safe integers remain accepted; JSON schema advertises the maximum. Tests cover the boundary.
- **Approved diagnostic change:** SDK input-validation messages differ, but retain `isError: true`, MCP `-32602`, and field paths. The in-memory SDK regression verifies these and checks a submitted private sentinel is not echoed. It checks `fleet_batch` JSON schema advertises the existing 50-item maximum. No prose equality is promised.
- Defaults in the inspected app schemas are already output-typed and no `.default(...).optional()` combination or transformed default was found. `strict` and `passthrough` remain supported but deprecated; issue format text and strict object APIs can be migrated in a later scoped change. No app calls Zod `.errors`, `.flatten`, `.format`, `errorMap`, or `ctx.path`. Existing `unknown` inputs and v4 default UUID/int differences are handled above.
- `src/mcp/zod-migration.test.ts` verifies oversized constrained arrays reject before an element transform runs, ordinary bounded input succeeds, representative GUID/unknown compatibility and safe-int boundary, and in-memory SDK schema/error behavior. This test uses `zod/v3` solely to compare simple historical behavior; production schemas use patched v4.

## Zod release review and outstanding compatibility decisions

The npm registry lists 58 stable v4 versions through 4.6.7. GitHub publishes release bodies for 55; fetched all 55 bodies and triaged their documented changes, including the 4.0, 4.1, 4.3, 4.4, 4.5, and 4.6 release narratives and patch commit descriptions. This is not a proof of every unnamed patch commit: some bodies give only a commit or issue number and the release summaries do not always identify behavior. GitHub has no release bodies for 4.0.0, 4.0.2, or 4.1.6. The [4.0.1 release](https://github.com/colinhacks/zod/releases/tag/v4.0.1) states 4.0.0 contained the same package code as 3.25.76 (while the default import switched from v3 to v4); [4.0.1...4.0.3](https://github.com/colinhacks/zod/compare/v4.0.1...v4.0.3) reconstructs 4.0.2 from the intervening commit list, and [4.1.6 PR](https://github.com/colinhacks/zod/pull/5222) records fixes for async codecs, optional defaults, and legacy TypeScript resolution. The [4.1.5...4.1.7 comparison](https://github.com/colinhacks/zod/compare/v4.1.5...v4.1.7) supplies surrounding history. Thus missing release bodies and unnamed commit details remain concrete upstream evidence gaps, not a claim of exhaustive semantic equivalence.

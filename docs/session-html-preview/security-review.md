# R1 — session HTML preview implementation security review

Scope: final released UI and bridge implementation versus base `9693fbb`, including new/untracked source and tests, frozen `preview-protocol.ts`, `ui-handoff.md`, and `backend-handoff.md`. Reviewer `/root/remaining_review`, Tier 2 / `gpt-6.1-sol` / `max`. All application/test files were read-only. No install, test execution, server, browser, E2E, database or Git mutation was performed by R1. Only this report was written.

## Threat model

The local OS registrant intentionally exports one host HTML file, but its active contents remain untrusted in the viewer. Relevant assets are dashboard DOM/storage/credentials, encrypted endpoint capabilities, unrelated host files, private registration paths, session metadata/lifecycle and bridge/browser availability. Remote callers must already have a verified approved endpoint and the target bridge's read permission; only verified local-CLI control authority may register/clear paths. Same-UID OS users and hostile privileged filesystem races are outside the approved boundary. Sources may attempt parent access, messaging, network activity, malformed oversized responses or traversal; callers may attempt cross-context/stale reads and races with registration/removal. The boundaries reviewed are encrypted admission/dispatch, file selection and bounded reads, session mutation serialization, wire projection, chunk assembly, and sandboxed rendering.

## Decision and findings

**No blocking security finding was confirmed in the reviewed implementation.** The code implements the agreed local-only registration, E2EE read transport, exact-file/root constraints, generation/revision fencing, private path projection and opaque `allow-scripts` iframe. This is source-review approval, conditional on root's outstanding real browser/transport/runtime gates. Unit/build outcomes below are worker-reported evidence, not tests R1 independently executed.

Accepted architectural limitations are unchanged: an arbitrary script can navigate its own iframe and consume browser CPU/heap; initial-document CSP is not blanket network isolation or execution termination. Polling cannot prove that an in-place producer finished writing. Use atomic producer rename for complete publication. Previously authorized/in-flight data cannot be retroactively retracted after a later clear/revocation. No vulnerability is inferred solely from one of these explicitly accepted limitations.

## Source-to-sink review

### Browser document and response handling

- `ui/src/lib/session-preview.ts:39–42` constructs the literal trusted doctype/head/CSP/referrer prefix before every untrusted byte. There is no parsing/extraction of an untrusted head in the parent. The policy denies ordinary resource destinations, connection APIs, nested frames/objects, workers, forms and base changes while allowing inline scripts/styles and data images. Its untrusted string is consumed only by `srcDoc` in `ui/src/components/SessionWorkspace.tsx:77`.
- The iframe has the exact constant `sandbox="allow-scripts"`, no origin/form/popup/top-navigation privileges, and `referrerPolicy="no-referrer"` (`SessionWorkspace.tsx:77`). The filename is a React text/title value (`:75,77`), not HTML. No credential/path is injected into the document and no new window-message receiver or parent host capability is introduced. The earlier design review's all-occurrence message search found service-worker/MessagePort/socket handlers rather than a dashboard window message command interface; the UI diff adds none.
- Descriptor validation rejects invalid IDs, slashes/backslashes, control characters, empty/dot basenames and >255 UTF-8-byte names (`session-preview.ts:8–10`). `useSessions.ts` now drops invalid preview registration state rather than retaining a previous trusted frame; its new merge/invalid-descriptor regression is in `useSessions.test.ts:475–487`.
- Status parsing requires the expected registration, revision syntax and an integer byte length ≤1 MiB (`session-preview.ts:12–18`). Chunks must match requested registration/revision/total/offset and boolean completion; base64 length is bounded before decoding, re-encoding proves canonical form, exact decoded length and `done` are enforced (`:20–32`). The caller starts at offset zero, advances only by verified bytes and handles the explicit empty-file chunk (`useSessionPreview.ts:67–78`). There is no attacker-controlled unbounded assembly loop.
- SHA-256 is checked over assembled bytes before one fatal UTF-8 decode (`session-preview.ts:34–37`; `useSessionPreview.ts:79–83`). Thus multibyte chunk boundaries, mixed/truncated bytes and replacement-character decoding cannot silently produce a rendered document. Returned raw error details are discarded (`useSessionPreview.ts:44–47,86`), so a server error cannot become injected markup or a path-bearing UI message.
- Identity includes bridge, session and registration (`useSessionPreview.ts:18`); the render-time boundary increments for client/user/visibility/readability/document visibility/security-generation changes (`:22–27`). State is exposed only for that epoch (`:99`), and each network/digest await rechecks activity before issuing another request or rendering (`:57–58,71–72,80–81`). Cleanup clears scheduling; polling is scheduled after completion with one logical assembly and coalesced manual refresh (`:33–96`). This prevents a completed response for an old target or revoked/disconnected state from activating an old iframe. It correctly does not claim cancellation of an already published command.
- `Dashboard.tsx:1077` gates readability on the connected command client, active bridge and ready security state; Terminal P2P connectivity alone does not grant a preview route. Workspace passes only that target/client into the hook (`SessionWorkspace.tsx:24–28`). Target/hide/security changes remove the previous ready view before a new target's document is committed. An unchanged poll preserves its key; manual refresh deliberately changes it (`useSessionPreview.ts:62–65`). Actual DOM/CSP behavior remains a browser test requirement.

### Registration, encrypted authorization and egress

- Direct registration/clear is exactly PUT/DELETE on the preview path with control permission (`bridge/src/security/bridge/permissions.ts:30–31`). `LocalApiServer.dispatchSecure` rejects a non-`local-cli` principal before HTTP adaptation (`local-api-server.ts:217–218`). This uses verified identity, not a caller-provided header/Origin. Generic direct HTTP remains retired by the existing request boundary.
- `mcp_request` cannot tunnel the preview route: the explicit deny is before `classifyHttp` (`permissions.ts:66–70`). Normal preview reads require a bounded session ID and read permission (`:71`); no browser-provided filesystem path is part of either read protocol. Existing security code binds the command/payload/bridge/session and validates permission before dispatch (`security/bridge/security.ts:126–136,165–197`).
- RPC payloads allow only the declared keys and validate exact bridge ID, ASCII session ID ≤200, preview UUID, lower-case SHA-256 revision and safe aligned nonnegative offset (`command-rpc.ts:88–109`). Controller methods also validate IDs/revisions/offsets, re-read registration and return typed safe states (`session-controller.ts:352–384`). Missing/cleared/replaced registrations do not create a file-read capability.
- The existing `executeSecurePacket` authenticates admission before dispatch, then encrypts its response (`security/bridge/execute.ts:13–28`); `sealTo` revalidates the recipient after preparing the encrypted response (`security.ts:229–234`). Plaintext broker consumers remain retired. A revoked endpoint during an awaited read therefore cannot acquire a newly released authenticated response through this path. Root/worker encrypted tests remain necessary evidence for the composed path.
- CLI input requires a valid session selector and path XOR clear, probes explicit `sessionMetadata.preview === true`, then uses its existing encrypted local API (`sessions-commands.ts:214–245`). Relative input resolves from CLI cwd; the bridge still confines it to the selected working directory. Old/malformed capability responses do not silently mutate an older bridge.
- The private source field is removed centrally by `toWireSession` (`session-wire.ts:12–14`) and explicitly from archived records (`local-api-server.ts:590–596`). Ordinary session reply/update paths continue to use that sanitizer. Registration's public metadata is only a newly generated UUID plus a safe basename (`session-preview.ts:54–62`). Errors from the file reader are converted to `PreviewError('Preview unavailable')`/reason codes (`:16–19,42–45,101`); the source path is not sent in those errors. Archive cleanup has a dedicated encrypted regression test, reviewed below.

### Filesystem, bounds and revision consistency

- Registration requires a normalized absolute source path and explicit working directory, checks a .html/.htm extension and bounded basename, computes the canonical root, and rejects a lexical escape (`session-preview.ts:52–67`). `contained` uses `path.relative` component semantics, not a vulnerable string prefix (`:20–23`).
- `validatePaths` checks bounded absolute canonical source/root strings, working-root equality, root type, every component below the root, final regular-file type, and canonical final path (`:24–41`). Every refresh repeats these checks (`:79`). Parent/final symlink traversal is rejected under the agreed non-hostile-race model. Hard links and malicious same-UID rename races are not represented as solved OS isolation boundaries.
- The final open uses read-only/no-follow/nonblocking flags (`:73`); descriptor stat must be regular and ≤1 MiB before allocation (`:80–85`). The buffer is fixed at max+1 and the read loop cannot exceed it, so growth after stat is bounded (`:85–92`). Pre/post descriptor and current-path metadata checks reject replacement/change during the sampled read (`:93–96`), then full bytes receive fatal UTF-8 validation and SHA-256 (`:97–99`). Descriptor close and read-counter release are in finally blocks (`:100–102`).
- One production controller/reader is shared by local and RPC dispatch (`index.ts:852–866,987–990`). Its reader admits at most four active file reads with immediate busy rejection rather than a file-read waiting queue (`session-preview.ts:75–77`). This is an active file-I/O limit, not a claim of a general authenticated RPC flood quota or a browser JS memory limit.
- Each returned chunk slices at most 98,304 raw bytes and is bound to the requested revision (`session-preview.ts:108–114`). Status computes the current digest rather than relying on mtime (`:105–106`). The exact body fields are bounded; max content base64 is 131,072 characters, comfortably below the 300,000-byte internal HTTP JSON cap and 450,000-byte encrypted-envelope cap. Existing crypto rejects actual oversized serialized envelopes. There is no whole-document broadcast or new resource URL.
- A re-registration always gets a new preview ID; clear deletes both public/private descriptors (`session-controller.ts:314–339`). Reads capture registration under the session queue, perform bounded I/O outside it, then re-enter the queue and compare both ID/private source and working directory (`:343–383`). If a clear/remove/replace happened before this final check, no old bytes are returned. This is the explicit read linearization point, not retroactive retraction after a later mutation.

### Shared session queue and lifecycle preservation

- `withSessionMutation` factors the old update queue without changing its error recovery (`session-controller.ts:215–227`). Update, registration, clear and remove all use that queue. The real executable injects the same pump queue into the controller and resurrection engine (`index.ts:830–838,852–866`). The pump queue is non-reentrant and serializes by session ID (`terminal-pump.ts:112–123`).
- Usage collection remains outside the slow lock, then reloads the current record before save/publish and skips deleted/nonterminal sessions (`session-controller.ts:156–164`). Retry loads and relaunches inside the queue (`:180–199`). The unchanged relaunch helper persists the loaded session, so current preview fields are retained; it does not recursively acquire the pump queue (`create-ftown-session.ts:346–384`). Runner completion callbacks enqueue their own fresh-state updates rather than being awaited under the caller's queue (`terminal-pump.ts:167–179`).
- Removal wraps the existing removal dependency once (`session-controller.ts:304–311`); its store lock is separate, and the retirement test's old external pump prelock is removed. This avoids nesting the same queue while preventing a stale registration success after retirement.
- Startup resurrection takes the same queue for each chosen session and `resurrectSession` **reloads** inside it (`session-resurrection.ts:55–61,174–184`); retired-automation mutation reloads similarly (`:113–132`). Thus an original list snapshot does not overwrite a newer registration. Error cleanup reloads before marking state. No sidecar reconciliation or unrelated lifecycle redesign was introduced.

## Least privilege

Preview status/chunks require existing read authority, not `bridge_exec`, control or admin. Path registration/clear requires both control and verified local-CLI kind. No new token, public URL, CORS exception, filesystem broker, iframe origin privilege, postMessage command channel, dependency or server is added. Raw HTML content stays in explicitly requested encrypted responses rather than broad session publications. These grants match the approved scope.

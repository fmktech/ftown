# Bridge discovery: session HTML preview

Read-only discovery at base `9693fbb`; proposed interfaces below are design recommendations, not existing APIs or a frozen contract. No source, dependency, runtime, or test changes were made. Root owns integration and E2E. Agent owns only this report.

## Existing flow and constraints

- Agent-facing CLI is `ftown sessions` in `bridge/src/sessions-commands.ts:138–190`; `selfSessionId` defaults to `FTOWN_SESSION_ID` or accepts explicit `--session-id` (`:207–213`). Its `pr` command capability-checks GET session then PATCHes it (`:223–253`), a useful UX pattern. `cli-client.ts:27–53` wraps local API routes in an authenticated `localApplication`, which uses a pinned local CLI identity, fresh hello, and encrypted envelope (`security/bridge/local-client.ts:9–40`). The variable `FTOWN_SESSION_ID` is a selector, not an independently verified identity: same-user local CLI authority can target other sessions; do not claim process/session-level authorization from it.
- CLI HTTP route → `BridgeSecurityService.requirement` → `classifyHttp` (`security/bridge/security.ts:121–142`, `permissions.ts:16–57`) → principal revalidation → `LocalApiServer.dispatchSecure` (`local-api-server.ts:209–265`) → internal route handler. Non-local principals cannot supply `callerSessionId` (`security/bridge/security.ts:170–173`), but `classifyHttp` itself receives only method/path; a new registration path cannot be restricted to local CLI merely by adding it to that classifier. Enforce endpoint kind `local-cli` using the verified `message.principal` before dispatching any register/clear route; authenticate and authorize **every** content read separately. Deny other endpoint kinds even if they possess `control`. Existing `executeSecurePacket` supplies validation/revalidation/response encryption (`security/bridge/execute.ts:6–43`).
- Dashboard cloud and local browser flows send `Command`s, not arbitrary HTTP: `index.ts:975–990,1010–1013` and `command-rpc.ts:189–204` show command → controller → encrypted response; `centrifugo-client.ts:306–335` receives only matching owner/recipient packets. Permission table `security/bridge/permissions.ts:4–11,60–74` fails closed for unknown commands. Add an explicit read-only operation and session ID validation there, add matching command/payload types to `bridge/src/types.ts`, handler in `command-rpc.ts`, and browser message types/adapters. Direct terminal transports explicitly reject non-terminal routes (`security/bridge/security.ts:121–125`); do not assume they carry the preview command.
- `Session` persists `workingDir` and metadata (`bridge/src/types.ts:32–58`); the session store writes complete `session.json` using same-directory temporary rename and serialized directory writes (`session-store.ts:20–25,51–94`). Controller serializes session load/mutate/save/publish through `withSessionWrite`, when supplied (`session-controller.ts:198–214,276–284`); terminal lifecycle uses the same higher-level queue (`terminal-pump.ts:56–62`). A raw independent `saveSession` call can overwrite newer metadata; keep new registration updates inside the controller's same queue. The store's lock does not alone serialize a load–modify–save spanning independent callers.
- Removal archives the `Session`, then deletes its session directory and emits the removed update (`remove-ftown-session.ts:19–56`, `session-store.ts:173–187`). Revival creates a **new** session using selected archived launch fields, not arbitrary fields (`local-api-server.ts:809–825`); suggest preview starts unregistered after revive. Retry of the same session may keep registration. Cleanup and stale reads must never recreate retired session directories. Stop/completion should not clear a preview: the user wants to see the finished output.
- `toWireSession` only removes `env` (`session-wire.ts:3–14`). An absolute preview path placed directly on `Session` will otherwise leak in encrypted list, GET, update, broadcasts, and archives that pass through this projection. This proposal distinguishes the persisted private location from a sanitized `preview: { registered: true } | null` wire field, and audits every session return/publication plus archive egress; no browser response, log, error, JSON schema, or event may include host path or path-bearing raw exception. Existing session `workingDir` is already a wire field; the new contract must not introduce a further path leak.
- Changes to registration should persist then `publishSessionUpdate` (encrypted per owner, `centrifugo-client.ts:156–181,224–233`); local events follow the same publication path. The UI merges snapshots and handles removal/reconnect (`ui/src/hooks/useSessions.ts:270–325`). There is no existing filesystem change watcher for preview contents. Use bounded client-driven encrypted polling while an eligible preview is open; no permanent per-file watcher is needed for v1. Reconcile on reconnect. Only publish registration state; never send HTML or private paths in a broad session update.
- `prepareWorkingDir` stores a normalized absolute working directory only when supplied (`create-ftown-session.ts:134–153,430–458`); it can be absent. A missing working directory is not a verified confinement root. Require a resolved explicit session root or a reviewed alternative root; do not silently fall back to bridge `process.cwd()` or real user home. Fail registration with a generic typed error if unavailable. The CLI may resolve an input path locally, but host path remains in encrypted request/private storage only.

## Proposed smallest lifecycle

1. **Register/replace:** `ftown sessions preview <path> [--session-id <id>]` selects session as above, checks a capability (`GET /api/sessions/:id`), sends an encrypted local-only `PUT /api/sessions/:id/preview` body `{ path: string }`. For compatibility, CLI accepts a path relative to session working directory; absolute input must resolve under that same root and never be shown by the server. Require one regular HTML file and validate without returning the resolved path. Store a private, versioned registration in session-scoped state with owner-only permissions and atomic replacement. Broadcast only sanitized registered status after durable success.
2. **Clear:** `ftown sessions preview --clear [--session-id <id>]` sends encrypted local-only `DELETE /api/sessions/:id/preview`. Idempotent for an existing session; unknown session returns not-found. Clear invalidates any outstanding reads/generations and emits sanitized state. Neither deleting registration nor removing the session deletes the user's HTML/assets.
3. **Read / change:** add read-only encrypted command `session_preview_status` with `{ bridgeId: string; sessionId: string; knownRevision?: string }`; response is a discriminated union `unregistered | unchanged | ready | missing | too_large | unavailable`, where `ready` carries an opaque digest revision and byte length (never path). `session_preview_chunk` with `{ bridgeId, sessionId, revision, offset }` returns `{ revision, offset, totalBytes, dataBase64, done }`; validate safe nonnegative offsets, enforce sequential bounds and current revision. Suggested one-megabyte maximum HTML, 96 KiB raw chunks. Validate UTF-8 for the full assembled document, and verify total length and digest before render. For each chunk, reopen and read a bounded full file, compute the digest, and require it to match `revision` before slicing; if changed between chunks return `stale_revision` so the client discards all assembled bytes and begins again. An immutable bounded snapshot could replace repeated reads if it has explicit owner, TTL, memory/concurrency bounds and invalidation. A read grant is sufficient; registration/clear need local CLI control. Name exact types in shared `bridge/src/preview-protocol.ts` rather than ad hoc `any`. Every request rechecks registration, confinement and principal; old revisions fail after re-register, clear, deletion, or replacement. Never accept a remotely supplied filesystem path.
4. **Polling:** root-selected active-visible interval approximately 1 second and one outstanding status request per selected bridge/session. Hash the actual bounded HTML bytes rather than `mtime` alone; same-size edits can occur. A change creates a new revision, fetches the complete coherent document, and replaces the iframe once (resetting state per brief). Readers must discard stale responses after a selection switch/close/clear or revision change. Restart recovers registration and polls lazily; no timers/watchers should survive session removal or app shutdown. Writes may be in-place: pre/post stat checks plus two identical polls can reduce torn/intermediate reads, but **cannot prove the producer finished** if it pauses mid-write. Reliable completed-file semantics requires producer atomic rename or an explicit completion signal; document the chosen v1 guarantee and test it.

### Bounded transport and asset strategy

`crypto.ts:7–8,97–108,193–205` caps the **serialized encrypted envelope** at 450,000 bytes, including ciphertext base64 and headers. Internal HTTP dispatch additionally rejects response JSON above **300,000 bytes** (`local-api-server.ts:248–255`); the 2 MiB incoming body cap at `:111–123` is not the response budget. Cloud command replies are also encrypted (`centrifugo-client.ts:327–332`), not the terminal truncation helper. Base64 content expands once in JSON and again in envelope ciphertext. Root selected 96 KiB maximum raw chunks: ~131 KiB content base64 and ~175 KiB envelope ciphertext plus bounded metadata, below both limits; implementations must calculate actual serialized bytes and reject, not rely only on estimates. Root proposed a 1 MiB total HTML limit and bounded concurrency; never allocate an unbounded file. Polling requests must not amplify disk/CPU/memory without active viewers.

**Architect v1 decision:** a single self-contained UTF-8 HTML document with inline CSS/JS and data images. Sibling assets, external scripts/styles/images, relative modules and dynamic resource fetching are outside this version; no sibling asset server, filesystem broker, asset package, or public preview endpoint. Frame isolation and network blocking must be frozen with the P3 security review. Missing file at startup/reconnect returns `missing` without deleting registration; reappearance at the same registered path becomes available automatically after an authenticated poll. Non-UTF-8 or oversized content returns a bounded generic error without file details.

## Confinement and race requirements

Use session-root confinement, reject empty/null/NUL, absolute escape, `..`, malformed separators, nonregular files, symlink escapes, directories, pipes and oversized inputs. Verify registration target and every document read; parsing/URL decoding must not permit encoded traversal or cross-root references. `usage-collector.ts:241–249` uses `realpath` + `stat` followed by later path-based read (`:255–258`); it illustrates basic containment, **not race-safe containment**. `O_NOFOLLOW` protects only the final component; parent directories can be replaced between checks/open. Root scopes the v1 boundary to an OS-level trusted local registrant and excludes hostile privileged concurrent filesystem races, while requiring ordinary symlink traversal and accidental secret-publication prevention. `realpath` containment, regular-file checks, no symlinks under the root, and descriptor-based reading with final-component no-follow reduce accidental escape but must not be described as race safe. P3 must independently review this boundary. Atomic writes do not solve malicious symlink swapping. Keep underlying errors private and bound per-file work before allocation.

## Draft-contract feasibility check (before freeze)

### Exact capability probe

Existing encrypted `GET /api/sessions/:id` returns a per-bridge capability object under `sessionMetadata` (`local-api-server.ts:710–721`). Add `preview: true` alongside `pullRequest: true`, not conditional on whether this session is registered. Extend `requireSessionCapability` (`sessions-commands.ts:223–229`) to accept `'preview'`, strictly check `capabilities?.sessionMetadata?.preview === true`, and issue a generic `bridge_upgrade_required: Upgrade this bridge to support HTML previews` if missing, false, null, or malformed. CLI validates path XOR `--clear` and the session ID before probing, then probes before PUT or DELETE; no mutation occurs against an old bridge. GET 404 remains “Session not found”, and authentication/network errors remain actual errors rather than incorrectly labelled upgrade. Unit tests should simulate old/malformed capabilities and prove no subsequent write, then present capability and verify exact PUT/DELETE. `sessionMetadata` in the wire response is already bridge-wide support on an existing-session lookup; `Session.preview` is instance state and must not serve as capability evidence.

### Clarifications required at the frozen boundary

1. `status` and `chunk` results must use `state` discriminants consistently, including `{state:'ready', previewId, revision, totalBytes}`, `{state:'unchanged', ...}`, `{state:'unavailable', previewId, reason}`, `{state:'unregistered'}`, `{state:'chunk', ...}`, `{state:'stale_revision'}`. State exact required keys in the compiler-enforced shared contract. `unregistered` from status may mean ID mismatch or no registration; chunk stale includes replacement, clear, deletion, and file digest change. Unknown-session status maps to the existing RPC `CommandResponse` rather than HTTP: specify e.g. `success:false`, generic error and `data:{code:'not_found'}`. Current command envelope has `requestId`, `success`, `data?`, `error?` (`types.ts:176–181`) and no HTTP status. HTTP-local registration can return actual 404/413.
2. Freeze controller signatures returning explicit wrappers: e.g. `Promise<SessionControllerResult<{ preview: PreviewStatus }>>` / same for `PreviewChunk`, plus a typed preview registration failure such as `too_large` → 413. Existing `SessionErrorCode` (`session-controller.ts:27–35`) contains only `not_found | invalid | conflict | automation_removed`; do not invent a 413 from an untyped thrown filesystem error. Specify sanitized busy/unavailable and invalid-request codes; do not turn malformed RPC input into host-path exceptions. Add read command names to bridge `CommandType`/payload and `security/bridge/permissions.ts` read list, bound payload `sessionId` to the same ASCII token/200-character envelope maximum and make exact `bridgeId`, sessionId, previewId binding mandatory.
3. Validate preview UUID and lower-case SHA-256 hex64, `knownRevision` when present, safe integer offsets and 98,304 alignment, forbid offset at/beyond `totalBytes` except offset 0 when total=0, and exact allowed keys. Bound source paths and basename by **UTF-8 bytes**, specify a control-character-free sanitized basename, and check descriptor/source ID equality and canonical working-root match on every read; inconsistent stored registration fails closed with generic `unavailable`. Limit reads even if the file grows after `fstat`: cap the descriptor read at 1,048,577 bytes and reject if it exceeds 1,048,576. Fatal UTF-8 + SHA-256 must be computed on the exact bytes used for the returned chunk.
4. `toWireSession` alone is insufficient: `GET /api/archive` (`local-api-server.ts:584–593`) copies each tombstone and deletes only `env`. Explicitly omit `previewSource` there too, preserving `removedAt`, and cover archived egress, direct GET/list, command reply, session update and reconnect. `session-wire.ts` may expose a typed `WireSession = Omit<Session, 'env' | 'previewSource'>`; its public descriptor must never contain source paths or internal error details. Keep base name safely escaped by UI rendering.
5. The current register/update serialization cannot alone meet delete races: controller `update` uses `withSessionWrite` (`session-controller.ts:198–214`) but `remove` directly invokes the removal dependency (`:289–296`). `SessionStore.saveSession` silently returns for retired IDs (`session-store.ts:66–68`) and delete has its own write lock (`:173–177`). A load-before-delete followed by post-delete save can therefore yield a false success/stale publication. Freeze a single writer/linearization strategy spanning register, clear and remove, with a meaningful persisted/deleted result; recheck both ID and source after each asynchronous document read before returning bytes. Avoid wrapping `remove` indiscriminately in a non-reentrant pump lock: existing `session-store-retirement.test.ts:125` already calls it while holding that lock. Explicitly modify its caller/test or implement an internal locked/unlocked split; test concurrent registration/removal and read/clear for no stale advertisement/old bytes. If a clear races *after* a successful final read check, that check is its defined linearization point; do not promise impossible retroactive erasure of already returned bytes.
6. Enforce endpoint-kind restriction at the `VerifiedApplication` boundary, before synthetic HTTP adapter and for all `PUT`/`DELETE` preview routes; the lower-level handler has no principal argument. `classifyHttp` must separately recognize only PUT/DELETE on exact session preview path as `control`; reject preview requests tunneled via `mcp_request` or any non-`local-cli` principal, regardless of `control`, and never expose the path as a GET/body or accept a browser-controlled path. `handleRequest` already rejects general direct HTTP routes with 426 (`local-api-server.ts:439–492`); preserve this.
7. V1 root/reader rules explicitly allow missing later file while retaining registration, support only a regular HTML document, and apply maximum four active reads per bridge to both status and chunk. An implementation-level pre/post stat comparison cannot guarantee a paused in-place writer has finished; require/document atomic rename for reliable completion and debounce only as a heuristic. `srcdoc` content paths must not become a capability or contain parent credentials. The security reviewer owns final CSP/sandbox and external navigation wording.

### Concrete serialized mutation proposal (architect follow-up)

The smallest approach that preserves the draft's `Session.preview` and `previewSource` fields is one shared non-reentrant per-session mutation queue across **all** existing-session load/modify/save writers, not only registration and deletion. Factor `SessionController.update`'s queue selection into a generic private `withSessionMutation<T>` using injected pump `withSessionWrite` or the existing per-ID fallback queue. Run registration, clear, and `removeSession` load→write/delete→publish in that same queue. Production callers at `local-api-server.ts:741` and `command-rpc.ts:274` call `controller.remove` directly; `session-store-retirement.test.ts:125` is already externally holding the pump queue, so adapt that test to call directly. Never have a caller and callee both take the same non-reentrant queue. The store's `deleteSession` lock is separate. Local publication occurs before queue release and the cloud publisher queues in FIFO order, but cloud delivery is best-effort and reconnect reconciliation is still needed.

Also fix other stale-snapshot writers, otherwise a *later* save can silently erase a correct registration:

- `SessionController.usage` (`session-controller.ts:135–155`) collects outside the queue, then save/publish under the same queue after **reloading** the current session and rechecking that it remains terminal. Do not hold the lock for slow collection; handle deletion or retry without stale resurrection. Existing retirement test documents an intentional late publication and must be updated to the new desired behavior.
- `SessionController.retry` (`:172–189`) must perform its existing-session load and relaunch/save under that queue. `relaunchFtownSession` writes the snapshot (`create-ftown-session.ts:357–365`); check no nested acquisition around that call. Keep runner lifecycle behavior and existing rollback semantics.
- Normal startup sets `ready=true` before `resurrection.resurrectSessions()` (`index.ts:1017–1022`), so registration can overlap it. Inject the same per-session queue into `SessionResurrection` and serialize its stale/reattach/resume decisions and save/publish, including retired-loop cleanup (`session-resurrection.ts:45–50,54–71,89,112–129`). Avoid nesting the queue when delegating to `relaunchFtownSession` or helper `markSessionDead`; wrap at a single ownership boundary.
- Existing terminal completion/error and terminal-pump usage already reload under the pump queue (`terminal-pump.ts:146–160,167–176,214–227`), and the hook caller is under it (`index.ts:957–971`). The initial `createFtownSession` save occurs before the newly created session is observable (`create-ftown-session.ts:448–475`) and is not an existing-session mutation. Audit additional call sites, test forced schedules, and preserve distinct session IDs' concurrency.

After a bounded file read, re-enter this queue and verify session still exists and both public/private registration IDs and source match; the check is the response's authorization/registration linearization point. A clear occurring later cannot retract bytes already returned. A runtime principal must still be revalidated by existing `sealTo` (`security/bridge/security.ts:229–234`); test revocation during read. Tests should pause async usage collection, then register or clear, then release collection; pause retry/resurrection between snapshot load and write; and interleave register/remove and clear/read. Assert the committed descriptor/source survive or correctly disappear and the deleted session is not re-advertised. Include `bridge/src/session-resurrection.ts`, `bridge/src/session-resurrection.test.ts`, `bridge/src/index.ts`, and affected controller/retirement tests in the exclusive bridge writer's scope. This proposal expands an existing shared queue rather than introducing sidecar reconciliation or generation-order contracts.

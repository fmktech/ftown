## Identity and UI

- `ui/src/components/SecurityDevices.tsx:31-35,185-206` chooses account view when `accountClient` and `accountState` are present, otherwise separate per-computer approval view. The account view merges three computer sources: live `bridges` from Dashboard (hostname as label), signed trust checkpoint bridges (fallback signed label), and browser-local legacy pins (fallback `Computer`). `Dashboard.tsx:207-212` constructs live security bridge labels from `bridge.hostname`; `useBridges` supplies that data. The account access map can contain discovered/unpaired or blocked entries, not just approved roster members (`SecurityDevices.tsx:256-271,293-303`).
- Browsers are signed `checkpoint.devices` keyed by `device.endpoint.id` with a signed `label`, not browser-local profile names (`SecurityDevices.tsx:244-255`). `accessBrowserLabel` in `SecurityAccessMap.tsx:21-28` adds fingerprint suffixes for generic names, and `:92-101,113-122` exposes the card, current-browser/computer indicator, accessible label and selected details. Place rename/reset in `AccountDevices` selected-browser/selected-computer details (`SecurityDevices.tsx:284-305`) and apply cosmetic overrides to the node label prior to `SecurityAccessMap` rendering. This preserves current indicators and existing id-based selection. Tests in `security-panel.test.tsx:222+` already model ready, offline, error, legacy, and account checkpoints; `security-access-map.test.tsx` tests labels and selections.
- A connected computer hostname comes from bridge presence (`Dashboard.tsx:207-212`); generic/offline fallback can come from signed roster. `/devices` page separately shows bridge-refresh hostname (`ui/src/app/devices/DevicesClient.tsx:7-12,84-88`), and `ui/src/components/SessionList.tsx:70-75` uses `BridgeInfo.hostname`. Decide centrally whether nicknames apply only to screenshot access map or these other surfaces; user authorized account-wide persistence, which does not inherently specify all screens. Never write `hostname` or change bridge ID/credentials.
- A signed label is security protocol material, not a mutable display field: `ui/src/lib/account-trust-store.ts:122-142` verifies enrollment against checkpoint member label; `bridge/src/security/account-protocol.ts`/`account-crypto.ts` encode labels in signed history. Never rewrite trust history, roster, endpoints, fingerprints, permissions, or cached trust to implement renames. Overlay absent names on existing fallback; reset means delete the override, not mutate signed label.

## Account ownership, eligibility, and trust boundaries

- `AccountTrustStore.readVerified(ownerId)` (`ui/src/lib/account-trust-store.ts:32-44`) loads `security_account_history` by owner, parses and verifies signed history, checks owner/root/revision/head, and returns current checkpoint. Browsers are eligible when `checkpoint.devices.some(d => d.endpoint.id === id)`; computers when `checkpoint.bridges.some(b => b.bridgeId === id)`. Deleted/revoked/non-roster objects must not become eligible because a name row or directory entry exists. Use owner and kind + ID throughout, and keep names cosmetic/untrusted; rendering them must not grant authority or change lock/edge states. Client should apply returned metadata only to already-present locally verified nodes, not use metadata to create nodes.
- Legacy `state.legacyBridges` is local IndexedDB-derived pin state (`account-security-client.ts:7-13,95-99`) and unavailable for server-side authorization; separately approved browsers on a legacy bridge are not server-verifiable from that list. For owner-paired legacy computers only, an existing server-side option is active `bridge_refresh` scoped to authenticated user's immutable ID by joining `users u` on `u.email=b.sub`, checking `u.id::text=$1`, `b.bridge_id=$2`, `b.current_jti <> 'revoked'` (`bridge-refresh.ts:31-38,88-114`, `security/endpoints/route.ts:24-30`). This is paired/account ownership, not proof of account-trust sharing. Do not claim a browser is approved merely because `security_endpoint_directory` has a row: browser registration requires only account session and endpoint ownership (`security/endpoints/route.ts:32-40`), and the directory is discovery data (`security-store.ts:36-52`). Current UI also includes unpaired runtime discoveries, so show Rename only for eligible targets and make unavailable cases explicit. Determine whether user wants locally pinned but unpaired legacy computers; no safe server membership proof was identified for them.
- For authenticated browser routes, use `auth()` with `session.user.id` as owner. `accountOwner(request,true)` (`ui/src/app/api/security/account/_shared.ts:14-31`) enforces exact trusted Origin and session ownership for mutations; **its non-mutation path accepts a bridge bearer**, so use explicit browser-session-only authentication if nickname reads are intended only for browsers. `request-origin.ts:15-23` fails closed on absent/foreign/malformed Origin. `boundedSecurityJson` (`security-store.ts:26-35`) enforces JSON content type and streaming byte bound; `ACCOUNT_HEADERS` no-store and `accountRateLimit` provide nearby conventions. Valid session alone is account authentication, not proof that the caller possesses an approved browser signing key; this distinction matters if privileged nickname mutation must require account-approved-device proof. Cosmetic labels should never be used to make approval or routing decisions.
- Validate target eligibility from a freshly verified checkpoint; avoid time-of-check/time-of-use writes based solely on stale pre-read by checking the verified root/revision/head in the conditional SQL write or using another explicitly reviewed concurrency control. Filter reads/overlays against current verified roster; revoked names cannot authorize operations and stale rows need not be exposed as active devices. Legacy eligibility should check owner binding and nonrevoked refresh row as part of write. Owner scoping on every query is mandatory; cross-account ID, unknown ID, malformed names, bad origin and signed-out requests should be tested.

## Data and migration

- Additive independent table is the least invasive model: `security_device_display_names(owner_id TEXT NOT NULL, kind TEXT NOT NULL CHECK(kind IN ('browser','bridge')), target_id TEXT NOT NULL, display_name TEXT NOT NULL, updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), PRIMARY KEY(owner_id,kind,target_id))`. Store only overrides; reset is an idempotent owner-scoped delete. Use bounded normalized string rules and reject controls before storage; UI also has a local max length and renders text (not HTML). The exact Unicode/length policy and API errors need a frozen contract. A name must not affect canonical target IDs, pairing, signed hashes, or permission checks.
- Exact schema files: new `ui/migrations/0009_device_display_names.sql`, matching fresh schema in `ui/schema.sql`, and e2e bootstrap import/execution in `e2e/scripts/setup-db.mjs:23-28,74-85`. Existing additive migrations use `SET LOCAL lock_timeout='5s'` and `statement_timeout='30s'`; `ui/scripts/migrate.mjs:51-77` runs sorted migrations individually in transactions and tracks names. A new empty table requires no backfill. Old code runs with expanded schema; new code querying missing table needs a rollout strategy (e.g. separately land prerequisite migration, verify migrate succeeds before feature promotion, or explicitly safe feature fallback reviewed by root).
- Crucial deploy ordering: `.github/workflows/migrate.yml:9-17,20-33` starts on main, serialized with itself but concurrently with Vercel deployment; README:582-601 warns that additive schema does not make new app compatible with old DB and requires prerequisite migration success before feature merge/promotion. Do not claim a same-commit PR alone guarantees ordering. Isolated DB test should prove existing rows unchanged, migration/re-run success and owner isolation; `e2e/scripts/check-account-trust-db.mjs` and `e2e/scripts/pending-approvals-db.ts` show actual database and migrator checks. Root must verify exact localhost database/user/port and all effective selectors before commands that write schema; loopback check alone in `setup-db.mjs:14-21` does not prove intended DB.

## Suggested boundaries for architect contract

1. Propose `ui/src/lib/device-display-names.ts` (typed discriminated `kind`, IDs, name validation, owner-scoped store), `ui/src/app/api/security/device-names/route.ts` and its focused tests. Candidate surface: session-only `GET` returns owner-visible overrides; `PUT` accepts `{kind,id,name}`; `DELETE` accepts `{kind,id}` and succeeds idempotently, with strict unknown-key rejection, bounded bodies and no-store. Finalize exact response/error shapes, label limits, auth trust policy, and eligibility/atomicity centrally before dispatch.
2. Share contract types with client through a small UI-safe module; avoid importing server DB code into browser. Client/hook should fetch on opening access view and refresh, use owner/client generations and aborts to prevent cross-account or late-save bleed, report loading/error/success, and avoid silently treating a failed save as success. On network failure preserve existing verified labels; do not disable/rewrite access decisions. Account mode only until separately scoped local/solo behavior is defined.
